# ZeroFlush 与原生 RocksDB 对比基准测试结果分析报告

> **数据来源**：`output/zeroflush_m3_perf/benchmark_native.json`（2026-08-20）、`output/zeroflush_m3_perf/benchmark_zeroflush.json`（2026-08-21）
> **报告生成**：2026-08-21
> **测试引擎**：`source/rocksdb`（原生） vs `source/rocksdb-zeroflush`（ZeroFlush，`--zeroflush --zf_partitions=64`）

---

## 1. 核心结论摘要（TL;DR）

| 维度 | 结论 | 数据支撑 |
|------|------|----------|
| **写吞吐** | ZF 慢原生 **16~37 倍**，为当前最大短板 | fillrandom：vs256 3,387 vs 124,125 ops/s（36.6×）；vs1024 1,919 vs 30,255 ops/s（15.8×） |
| **读吞吐** | **混合结果**：vs256 下 ZF 快 **8.3 倍**；vs1024 下 ZF 慢 7.4 倍（存在测试时序干扰） | readrandom：vs256 96,554 vs 11,599 ops/s；vs1024 4,115 vs 30,250 ops/s |
| **读尾延迟** | vs256 下 ZF P99 快 **58 倍**（248us vs 14,433us），长尾极稳 | ZF P99.9=358us，原生 P99.9=161ms |
| **写放大** | ZF 0.70，比原生（0.81/0.82）**低 13~15%** | 两个 value size 下均稳定 0.70 |
| **空间占用** | ZF 35.2GB，比原生（40.6/40.8GB）**省 ~13%** | SST 仅存 key+locator，value 原样驻留 WAL |

**一句话总结**：ZeroFlush 以**写吞吐 16~37 倍的代价**，换取了**空间效率 13% 的收益与 vs256 读路径 8 倍的性能优势**；写路径是下一步优化的核心靶点。

## 4. 关键发现

### 发现 1：ZF 读路径在 vs256 下全面领先（P99 快 58 倍）

ZF 的 SST 仅存 key + SlimLocator，配合 Bloom filter 可极快速定位，value 从 WAL 分区定点读回。vs256 readrandom 的 P99=248us、P99.9=358us、P99.99=559us——**长尾几乎完全消失**，延迟分布极度紧凑。相比之下原生在 8MB cache 下随机读 40GB DB，P99.9 达 161ms、P99.99 达 430ms（块缓存全失效 + fill 刚结束的 compaction 干扰）。

### 发现 2：ZF 写路径慢的三个叠加根因

1. **L0 周期性 write stop**：ZF 每轮物化批量产生 64 个 L0 文件（每分区 1 个），flush 产生速率 > compaction 消费速率，L0 在 64↔128 间周期波动，每次触顶（stop=72）即停写等待 compaction（实测单次 L0→L1 compaction 耗时 170+s）；
2. **物化路径 WAL 读回开销**：memtable 仅存 key+WAL 位置，物化（`ZfMaterializeAllEpochs`）时需从 64 个 WAL 分区随机定点读回全部 value 再写入 SST；
3. **物化单线程**：LOG 显示 `compaction_time_cpu ≈ compaction_time`（如 job 81：172s wall vs 165s CPU），物化基本单线程执行，未利用 `max_background_jobs=16`。

### 发现 3：写路径 P50 暴露"常态慢"而非仅"尾慢"

原生 fill P50 仅 14~20us（多数写只碰 memtable）；ZF fill P50 达 1,440~1,894us，为原生 100 倍——L0 持续高位导致**每次写入常态性承受限速/停顿**，与发现 2 相互印证。

### 发现 4：vs1024 读异常慢是测试时序 + 读路径结构双重因素

ZF vs1024 readrandom 仅 4,115 ops/s（P50=3,654us），与 vs256 的 96,554 ops/s 相差 23 倍：
- **时序因素**：readrandom 紧跟 fill 结束执行，7.5h 填写产生的大量待完成 compaction 仍在后台争抢 IO/CPU（原生侧 vs256 的读慢 11,599 ops/s 同样受此影响）；
- **结构因素**：1KB value 的 WAL 定点读回成本更高，且 8MB block cache 对 key+locator 索引层几乎无缓存收益。

该数据点**不能**直接推断"ZF vs1024 读必然慢"，需在 compaction 稳态下复测（见优化建议 P2-b）。

### 发现 5：空间效率收益稳定且与 value size 无关

两场景 ZF 均为 35.2GB / w-amp 0.70：SST 侧每 key 仅 ~16B（key+locator），value 无重写、原样驻留 WAL；compaction 亦仅搬运 key+locator。原生需为每层 compaction 重写完整 KV。**ZF 的空间收益随 LSM 层数增加而扩大**。

### 发现 6：磁盘始终非瓶颈

全程实际磁盘写入远低于 NVMe 能力（953MB/s）：原生 ~79MB/s、ZF <5MB/s。ZF 写慢是**软件路径**问题（stop 等待 + 单线程物化），非硬件限制——这为 P3 优化提供了明确的性能上限空间。

## 5. 后续优化建议

### P2 — 配置级（立即可做，无需改代码）

| # | 建议 | 预期收益 |
|---|------|----------|
| a | `--cache_size` 8MB → 256MB+ | 改善两引擎 readrandom（尤其 ZF vs1024 的索引层缓存命中） |
| b | readrandom 前等待 compaction 队列清空（轮询 `compactions.pending` 归零或固定 sleep） | 消除发现 4 的时序干扰，获得稳态读数据 |
| c | ZF stall 触发器进一步抬升（如 slowdown=128 / stop=144） | 减少 L0 触顶频率（当前每 ~5min 一次 stop），平滑写延迟 |
| d | 两引擎同开 `--compression_type=lz4` | 降低磁盘压力，对 ZF 物化读回亦有收益 |

### P3 — ZF 代码级（写路径优化的根本解法）

| # | 建议 | 针对根因 | 预期收益 |
|---|------|----------|----------|
| a | **物化并行化**：按分区多线程物化（当前 `ZfMaterializeAllEpochs` 单线程串行） | 发现 2-③ | 物化吞吐 ×N（N=并行分区数），直接缩短 stop 等待 |
| b | **物化顺序预读**：物化前按 WAL 段顺序批量读 value（当前 `ReadValue` 逐条随机定点读） | 发现 2-② | WAL 读回从随机 IO 转顺序 IO，消除 100 倍 P50 差距的主要来源 |
| c | **value cache / 热点驻留**：物化前 value 先入块缓存 | 发现 4 结构因素 | 改善 vs1024 读路径 |
| d | **动态分区数或减小 `zf_partitions`**（如 16/32） | 发现 2-① | L0 文件基数下降，compaction 追赶压力线性减小 |

### 复测建议

P3-a/P3-b 完成后按同配置重跑 fillrandom：若物化并行 8 线程 + 顺序读，写吞吐理论上可提升至当前的 **5~10 倍**（3,387 → 17K~34K ops/s 区间），届时 ZF 写路径与原生的差距有望收窄至 4~7 倍以内。
