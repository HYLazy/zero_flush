# R59 修复与性能提升方案设计（R59b 计划）

日期：2026-09-02 · 作者：ZeroFlush 开发 · 状态：设计稿

## 1. 问题链回顾（R59 的教训）

R59 越界融合（a996b80）让融合从 0 恢复（281 次），但引入副作用链：

```
越界融合输出范围 = overlap 并集 ⊋ 分区范围
  → (a) 批内相邻分区输出范围相交 → 链式替换误杀 → 数据丢失（丢 5.3% key）
  → (b) 修复 1（收紧判据）→ 相邻输出不再被吸收 → 批内冲突 → kSkip 滞留
  → (c) 修复 2（无条件 kSkip）→ 滞留数据下批多代收养物化 → 物化占 wall 81%
  → 50GB/1KB 22.6K（正确）vs 39.4K（错误版，含丢数据收益）vs 12.3K（R59 前）
```

**当前瓶颈画像（修复版 b2bd1fe，50GB/1KB）**：

| 指标 | 值 |
|---|---|
| 吞吐 | 22,634 ops/s |
| 物化时间 / wall | 1,722s / 2,121s = **81%** |
| 融合（base_merge） | 281 次，重写 11.5GB（~41MB/次） |
| fallback（回落 L0） | 919 |

物化是唯一瓶颈；物化的膨胀来自 kSkip 多代收养（读 2-3 代 WAL、输出叠加）。

## 2. 方案对比

| 方案 | 机制 | 收益（预估） | 复杂度 | 风险 |
|---|---|---|---|---|
| **A. L1 对齐物化**（推荐） | 输出按 overlap 文件边界切分，1:1 替换 | 22.6K → **35-40K** | 中 | 物化读放大（同数据多文件重复读） |
| B. 批内尾部收养 | kSkip 数据批内最后一个 epoch 吸收 | 22.6K → 25-28K | 中 | 批内 B 侧包含逻辑复杂 |
| C. 物化提速 | kMaxBatch 全分区 + 并行度 | 22.6K → 25-30K | 低 | 批次联动需调参 |
| D. 去注册 | 融合不阻塞原生 L0→L1 | 辅助（L0 循环） | 高 | 批内竞态未闭环（R59x） |

**A+B+C 组合为推荐路线**：A 根治冲突（kSkip 大减）→ C 直接提速物化 → B 兜底残余滞留。

## 3. 方案 A 详细设计：L1 对齐物化

### 3.1 核心思想

当前越界融合：**一个分区物化 → 一个输出**（范围 = overlap 并集 ⊋ 分区 → 膨胀 → 冲突）。

对齐物化：**一个分区物化 → 每个 overlap 文件一个输出**——输出 f' 的范围 = overlap 文件 f 的范围，B 侧 = f 全部数据 + 分区新数据 ∩ [f_lo, f_hi)，1:1 替换 f。

**关键性质**：输出范围 = 被替换文件范围（不膨胀）→
- L1 保持无重叠（替换同一文件，无新增重叠文件）；
- 批内冲突仅在**共享同一文件**的分区之间发生（文件跨分区边界时）——频率从"必然"降为"仅共享"；
- 批内同文件重写由链式替换吸收（范围相等的融合输出：x ⊆ o ✓ + replaced 子集 ✓ + 都 kMergeBase ✓ → 后序 superseded 前序）——**前提是后序 B 侧含前序数据**（下批时成立：前序已安装，vstorage 可见；同批时不成立 → kSkip）。

### 3.2 物化流程（MaterializeMergePartition 重构）

```
输入：分区 p 的新数据（A 侧，WAL 读一次）、overlap 文件集 F = {f1..fk}
输出：k 个对齐文件 + 空隙文件
1. A 侧读入内存（一次 WAL 顺序读，同现状）
2. 对每个 f ∈ F：
   - 输出范围 [f_lo, f_hi)
   - B 侧 = TableIterator(f)（同现状）
   - A 侧切片 = A 中 user_key ∈ [f_lo, f_hi) 的部分（排序后二分）
   - 合并（A 侧优先——seq 更新）→ BuildTable → f'
3. 空隙 = A 中不在任何 f 范围的 key（分区边缘）→ 直装输出
4. 安装：f' 替换 f（DeleteFile(f) + AddFile(f')）；空隙直装（无替换）
```

### 3.3 决策层改动（PlanLocked）

- scan_overlap 保持 R59 语义（越界收进 overlap）；
- 融合决策：overlap 非空 → kMergeBase（对齐物化，multi-output）；
- **批内同文件检测**：共享集合记录"本批已决策替换的文件号"（`zf_batch_registered`，R59f 已实现）——后序分区 scan_overlap 命中共享文件 → **无条件 kSkip**（数据留 WAL，下批前序已安装 → B 侧可见 → 正确吸收）。这正是当前修复版逻辑，冲突频率因对齐而大减；
- kSkip 的数据不再滞留多代：gen 上限（kMaxSkipGenerations=2）强制落地。

### 3.4 物化读放大代价

同一 L1 文件被 k 个共享分区先后重写（k = 文件跨分区数，通常 1-3）——写放大 = k×文件大小/分区数据。对比：
- 现状（并集重写）：重写 (k×文件) 并集一次 + kSkip 滞留多代物化；
- 对齐（文件级重写）：每个共享分区重写整个文件一次（k 次 × 文件大小）——但**无滞留**（物化即时完成）。

k 通常 ≤3，且文件大小 ≈ 分区数据量级 → 写放大 ≈ 3× vs 现状的滞留放大（2-3 代）+ 物化时间减半 → 净收益。

### 3.5 实现步骤

1. **MaterializeMergePartition 多输出化**：A 侧切片 + 逐文件 BuildTable + 空隙直装（改动核心，~150 行）；
2. **MaterializeOutput 关联替换文件**：每个输出携带 replaced_file_numbers = {f}（1:1）；
3. **批内共享文件检测接线**：`zf_batch_registered`（R59f 代码仍在 git 历史，恢复）；
4. **安装循环**：multi-output 逐文件安装（flush_job 的 edit_ 循环已支持多输出）；
5. **空隙直装**：复用 kDirect 路径。

## 4. 方案 C 详细设计：物化提速（叠加）

## 6. 预期收益

- 50GB/1KB：22.6K → 35-40K（对齐消除滞留）→ 追平错误版 39.4K 且**零丢失**；
- 同窗 vs native（26.9K）：落后 1.19× → 领先 1.3-1.5×；
- 100GB/1KB：14.0K → 25-30K（同比例）；
- 物化 wall 占比 81% → ~50%（物化不再是唯一瓶颈）。

## 7. 风险与回退

- **物化读放大**：共享文件重写 k 次——若 k 大（文件跨 4+ 分区）则写放大恶化 → 加阈值：共享文件数 > 阈值时回落现状（并集重写）→ 可回退；
- **multi-output 安装原子性**：同批多输出必须单次 VersionEdit（现有批次原子安装已保证）；
- **空隙直装与 L0 交互**：空隙直装装 L1（无重叠）→ 若 L1 有运行时新增文件 → 验证（b）兜底装 L0（现有逻辑）；
- 每步可独立提交，A 失败则保留 B/C（增量收益不丢失）。
