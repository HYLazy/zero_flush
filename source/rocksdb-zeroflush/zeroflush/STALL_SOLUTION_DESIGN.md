# 滞留与物化规模退化解决方案设计（R59E）

日期：2026-09-02 · 状态：设计稿 · 目标：弥合 100GB 落后 native 10% 的差距

## 1. 问题定义与数据事实

同窗对比：50GB ZF 1.025×（持平）→ 100GB 0.907×（落后 10%）。关键数据：

| 指标 | 50GB | 100GB |
|---|---|---|
| 吞吐 | 27,066 ops/s | 19,701 ops/s |
| 物化时间 / wall | ~81% | 3,789s / 4,873s = 78% |
| skip | 4,049 | 6,260 |
| fallback | 839 | 1,605 |
| 物化速率（用户数据/物化时间） | ~30 MB/s | ~27 MB/s |
| 排序占物化 | ~9% | ~9% |

**物化速率规模退化（历史数据点）**：2.2GB 188 MB/s → 10GB 70 → 50GB 30 → 100GB 27 MB/s（7×）。
排序仅 9%——退化主因不是 CPU。

**滞留的角色未证实**：kMaxSkipGenerations=2 已封顶代深（收养 ≥2 代强制物化），
100GB 物化 3,789s ≈ 100GB ÷ 27MB/s（无 2× 放大迹象）——滞留的代深放大可能不是
主因，或与物化速率退化纠缠。**必须先归因再修复**（教训：R59B/R59D 未归因即实现，
6+ 轮未闭环）。

## 2. 归因实验（判别性，~2 小时）

### E1：物化 4s/epoch 的构成分解（100GB 现场）
对 100GB 规模（或 50GB）的物化加分段计时（临时打印，限频）：
- WAL 读（读字节/时间）→ 判断是否磁盘读瓶颈（页缓存不足：100GB > 54GB 内存）
- BuildTable Sync 次数/时间（文件数 = 952 epoch × 4 = ~3,800 Sync）
- 排序/合并（已知 9%）
- 任务调度间隙（epoch 间等待）
**判别**：若 WAL 读占 >50% 且含磁盘等待 → 页缓存不足的读瓶颈（非滞留）；若 Sync
占比高 → fsync 次数随 epoch 数线性 → 批次增大（epoch 变大）直接降本。

### E2：skip 代深与读放大（滞留的真实代价）
- PlanLocked 7 个 kSkip 点加原因计数（batch_skipped / !ok-原生占用 / l0_busy /
  ratio / 共享文件 / gen 上限 / 其他）——一次 5GB 定位主导；
- 统计收养物化的 gens 数分布（每 epoch 物化分区的代数 1/2/3+）→ 读放大 = Σ代/epoch。
**判别**：若 >90% 分区单代 → 滞留读放大 <10%（不是主因，聚焦物化速率）；若多代
普遍 → 滞留是主因之一，走方案 B。

### E3：批次粒度 vs 物化速率（epoch 大小）
kMaxBatch=4 → epoch 256MB（952 epoch@100GB）。batch=16 + epoch=1GB → epoch 数 ÷4：
- 若固定开销（Sync/调度）主导 → 物化速率应 ~2-3×（Sync ÷4 + 读不变）；
- batch=16 曾崩（批内冲突，R59C skip_ok 修复后可能已解）→ 重测。
**判别**：epoch 数对物化速率的影响 = 固定开销占比的直接度量。

## 3. 修复分支（按归因结果选择）

### 分支 A：物化读磁盘瓶颈（E1 证实）
页缓存不足时 WAL 读落盘——物化读与写 SST 交替造成磁盘抖动。方向：
- A1：**物化输入预取**——封存 WAL 在读前顺序预取（posix_fadvise SEQUENTIAL），
  减少读-写交替的寻道；
- A2：**epoch 内 WAL 读与 SST 写分阶段**（先读全部 WAL 到内存/缓冲，再写 SST）——
  当前是任务级交错；改分区内先读后写（读 256MB 内存化，8 worker × 32MB）；
- A3：接受规模退化（native 同受磁盘瓶颈——native 100GB 21.7K 也远低于小规模）——
  量化"绝对差距"而非"相对退化"。

### 分支 B：滞留读放大证实（E2 证实多代普遍）
- B1（代深即时封顶）：kSkip 时若该分区已滞留 1 代（recovery 中有其 gens）→
  不 skip，强制本批物化（走 kMergeBase 越界融合或 kFallback）——代深恒 1；
- B2（批内吸收）：skip 数据不跨批——FlushJob 收尾时若 skip_gens_ 非空，追加一轮
  小物化（仅 skip 分区，冲突应已消——前序本批已安装）。改造：WriteLevel0Table
  的安装后阶段加"skip 补物化"循环（复用任务池），预计 +30-50 行；
- B3（skip 阈值细化）：区分"必要等待"（前序未装，下批必消）与"持续冲突"
  （L1 错位，skip 无用）——后者直接走越界融合而非 skip。

### 分支 C：epoch 固定开销主导（E3 证实）
- C1：kMaxBatch 16 + epoch 1GB（R59C skip_ok 修复批内冲突后重测——当时崩溃于
  孤儿全范围输出，SafeRangeOf 已兜底）；
- C2：Sync 合并——同 epoch 多文件 Sync 批处理（fsync 已是 fdatasync，次数仍随
  文件数）——物化输出文件数 = 分区数/epoch 固定 4 → Sync 4 次/epoch × 952；
  改"epoch 收尾统一 Sync"不改变次数但合并窗口（文件写完攒批 Sync 需 WritableFile
  支持——RocksDB 无 batch Sync，跳过）；
- C3：target_file_size 增大 → 每 epoch 文件数下降（4→2）→ Sync ÷2。

## 4. 滞留专项设计（若 B 归因证实——B2 详设）

**目标**：skip 数据在同 FlushJob 内吸收，代深恒 ≤1（当前 ≤2 但跨批）。

**流程**：
```
阶段 2（安装后，持锁）：
  if (!skipped_gens_.empty()) {
    // 前序输出已安装（本批 VersionEdit 已 Apply）→ vstorage 可见
    // → skip 分区的冲突应已消（前序注册已释放）
    对 skip 分区重新决策（PlanLocked 语义，复用）：
      可融合/直装 → 追加物化（任务池）→ 安装（第二个 VersionEdit）
      仍冲突（原生占用等）→ 移交 recovery（现有路径，罕见）
  }
```
**要点**：
- 重新决策用安装后的 vstorage（持锁），前序输出可见 → 越界融合/直装正常；
- 追加物化的 gens = skipped_gens_（可能含多代收养）→ 一次合并；
- 第二个 VersionEdit 与首批同持锁窗口（原子性由 LogAndApply 保证）；
- 仍冲突的分区（<5% 预期）走 recovery（保留现有兜底）。
**收益**：skip 数据当批落地 → recovery 集合近空 → 下批无收养放大 → 代深恒 1 →
物化工作量 = 用户数据（无重复处理）。

**风险**：追加物化延长 FlushJob 持锁时间（物化在锁外——阶段 2 后解锁追加轮，
再锁安装——与现有阶段 1/2 结构一致，无新持锁风险）；追加轮的决策/物化/安装
复用现有代码路径（ZfMaterializeJob 单 epoch 实例化）。

## 6. 预期

- 若 E1 读瓶颈：物化速率 27 → 40-60MB/s（预取/分阶段）→ 100GB 吞吐 → 24-30K
  （追平 native）；

## 7. E2 归因结果（2026-09-02 实测，5GB sampled）

skip 196 次原因分布：**l0_busy=191（97%）**、batch_prev=5、其余 0。

**滞留链条修正**：滞留的直接机制不是"批内前序冲突"，而是
```
fallback（ratio 不足/kDirect 被挡）→ L0 文件产生
  → 后续同分区物化：L0 文件被原生 L0→base compaction 占用 → l0_busy
  → kSkip（数据积 WAL）→ 下批收养多代物化 → 物化放大
  → 物化慢 → 封存积压 → 更多 fallback → 自增强
```
fallback 235 次（决策 46% 装 L0）是循环源头：L0 残留挡直装（PickInstallLevel
L0..base 检查）→ 新 fallback；L0 被原生占用挡融合 → l0_busy skip。

**修复优先级（更新）**：
1. **P0：打破 fallback 自增强**——L0 残留一旦存在，后续同分区物化几乎必然
   fallback/skip。方向：a) L0 残留的即时清空（同分区物化时若 L0 有自己的旧
   文件且未被占用 → L0 融合（M4.9 已有，需确认触发率）；b) L0 被占用时的
   等待窗口缩短（原生 L0→base 消费很快——skip 的下批应已消，但 batch_prev
   只有 5 说明 l0_busy 的 skip 数据下批仍被挡——需要验证 l0_busy 的等待是否
   有效：原生消费 L0 后 vstorage 无 L0 → 直装恢复）；
2. **P1：fallback 源头归因**（下一插桩：kDirect 回落 vs kFallback 分支 vs
   ratio——235 次装 L0 的决策路径分布）；
3. **P2：滞留数据的有界性确认**（kMaxSkipGenerations=2 下代深 ≤2，但 l0_busy
   连续发生时数据反复跨批——收养代数是否实际 ≤2）。

## 8. P1 归因结果（2026-09-02，5GB sampled）

装 L0 的 272 次 **全部是 kDirect 决策后的 PickInstallLevel 回落**（dec=0 lvl=0
×272、dec=0 lvl=1 ×47 直装成功），0 次显式 kFallback。

**根因闭环（完整）**：kDirect 直装失败 = 安装时 L0..base 层有重叠——但决策
（阶段 0，持锁）时 scan_overlap/l0_overlap 均为空 → 重叠文件在**阶段 1（物化，
无锁 1-4s）期间被原生 compaction 安装**（新 base 文件与输出范围重叠）→
PickInstallLevel 的 OverlapInLevel 命中 → 回落 L0。R54 已知竞态的规模版：
原生 compaction 频率随规模增长 → 阶段 1 窗口内撞新文件的概率线性上升。

```
kDirect 决策（无冲突）→ 阶段 1 原生安装新 base 文件 → 安装时撞重叠
  → PickInstallLevel 回落 L0（272 次/5GB = 决策 46%）
  → L0 文件 → 后续同分区物化：L0 被原生占用 → l0_busy skip（190）
  → 滞留 → 多代收养物化 → 物化放大
```

## 9. P0 破环方案（下一实施，需先确认 FinalizeLocked/Apply 时序）

**方向：消除 kDirect 回落的两个子选项**
- P0a（安装期重决策）：阶段 2 安装（Apply）前，对 PickInstallLevel 回落 L0 的
  kDirect 输出**重新决策**——vstorage 含阶段 1 安装的新文件 → overlap 非空 →
  转融合路径（输出与重叠文件合并后替换）。需确认：输出文件已生成（物化产物），
  转融合 = 二次物化（读 WAL + 新重叠文件合并）——只对回落的 46% 分区做，成本
  可控（一次额外物化 vs 当前滞留的多次）。
- P0b（L0 即时消费强化）：回落装 L0 后，L0 文件由**原生消费**——l0_busy 的
  skip 数据下批应落地（原生消费完 L0 空）——验证"下批落地率"：若落地率高，
  滞留仅 1 批（代深 2 有界），物化放大有限——需量化 272 回落的落地延迟。
- 实施前先确认时序：FinalizeLocked 的 edit_ 是逐输出累积还是统一 Apply；
  kDirect 回落发生在 Apply 前（可拦截重决策）还是后。

## 10. 设备级归因（2026-09-02，50GB diskstats 采样）

50GB 页缓存下：磁盘**读 ≈ 0 MB/s**（WAL 写后即读命中页缓存——物化读不是
瓶颈）、设备写 303 MB/s。吞吐 26MB/s ≈ 303 ÷ 11.6（ZF 写放大）——
**ZF 写放大 ~11.6× vs native 9.8×（差距 12% ≈ 实测落后 10%）**。

写放大是 100GB 差距的直接度量。物化时间线性（50GB 34.4s/GB vs 100GB
37.9s/GB，代深 ≈1.1 无超线性）——滞留未造成物化放大，但 fallback→L0
循环贡献了写放大（L0 文件 → 原生 L0→base 全范围重写 → 深层下探）。

**P0a 优先级确认**：打破 kDirect 安装期回落（272 次/5GB → L0 → 重写）
直接降写放大。时序已确认：回落发生在 FinalizeLocked（持锁）内、
Apply 前——可拦截。实现方案：回落输出转 pending（不装 L0、不 AddFile）
→ 本批安装后（解锁）对 pending 分区用最新 vstorage 重新决策（此时
阶段 1 原生安装的文件可见 → overlap 非空 → 融合路径）→ 二次物化 →
安装。仅对回落分区（~46%）做，一次额外物化 vs 当前 L0 全范围重写 +
滞留多代——净写放大下降。

**验证计划**：50GB 前后对比（设备写 GB 与吞吐）——目标写放大 11.6 → <9，
吞吐 27K → 33K+；100GB 目标 ≥ native。
