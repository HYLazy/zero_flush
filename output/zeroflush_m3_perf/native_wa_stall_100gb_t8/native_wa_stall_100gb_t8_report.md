# 原生 RocksDB 100GB/1KB fillrandom：8 线程 vs 16 线程（三类写停顿对比）

唯一差异：写线程数（8 vs 16）；workload 同为 103,244,288 键 ≈ 100GB 用户数据；
后台 compaction 能力不变（max_background_jobs=24、subcompactions=16）。

## 1. 总体结果

| 项 | 16 线程 | 8 线程 |
|---|---|---|
| 吞吐 | 13,978 ops/s（13.9 MB/s） | 12,558 ops/s（12.5 MB/s） |
| wall | 7,386s（123 分钟） | 8,221s（137 分钟） |
| 停顿总时长 | 6,960s（94.6%） | 7,684s（93.7%） |
| L0 flush 写出 | 184.8GB | 184.1GB |
| SST 累计写出（总写放大） | 980.3GB（9.8×） | 1,007.0GB（10.0×） |
| compaction jobs | 3,762 | 3,834 |

## 2. 三类写停顿（WriteStallCause）

| 停顿类型 | 16 线程 delayed | 16 线程 stopped | 8 线程 delayed | 8 线程 stopped |
|---|---|---|---|---|
| **内存（memtable-limit）** | 0 | **2605** | 0 | **2595** |
| **L0 文件数** | 6 | 0 | 0 | 0 |
| **L1 以下（pending compaction 字节）** | 0 | 0 | 0 | 0 |
| 合计 | 6 | 2605 | 0 | 2595 |

- 停顿占比几乎不变（94.6% → 93.7%），**memtable stop 绝对主导的模式完全一致**；
- **L0 与 L1+ 停顿在两种线程数下都≈0**——停顿类型与线程数无关；
- 8 线程单次停顿更长（总停顿 7,684s ÷ 2,595 次 ≈ 2.96s/次 vs 16 线程 2.67s/次）——
  写组更小、突发写入更少，memtable 出清窗口内写入量更少；
- 停顿模式：开头 ~30s 全速写满 ~2.7GB memtable 预算，此后 94% 时间在等 compaction 出清。

## 3. 各层写放大对比（SST 写出字节 / 100GB 用户数据）

| 层 | 16 线程 | 8 线程 |
|---|---|---|
| L0 | 184.8GB（1.85×） | 184.1GB（1.84×） |
| L1 | 121.9GB（1.22×） | 122.7GB（1.23×） |
| L2 | 285.7GB（2.86×） | 303.0GB（3.03×） |
| L3 | 371.0GB（3.71×） | 382.2GB（3.82×） |
| L4 | 16.9GB（0.17×） | 15.0GB（0.15×） |
| 合计 | 980.3GB（9.80×） | 1,007.0GB（10.07×） |

- 各层写放大几乎一致（±3%）——写放大由 workload 与 LSM 参数决定，与写线程数无关；
- 8 线程 L2 略高（303 vs 286GB）：写突发更平缓 → L0 小文件分布不同 → L1→L2 输入重叠略增。

## 4. Compaction SSTable 数量对比

| 输出层 | 16 线程 jobs/输入SST/平均 | 8 线程 jobs/输入SST/平均 |
|---|---|---|
| L0 | 290 / 1393 / 4.8 | 282 / 1377 / 4.88 |
| L1 | 99 / 1052 / 10.63 | 108 / 1122 / 10.39 |
| L2 | 1719 / 5879 / 3.42 | 1778 / 6213 / 3.49 |
| L3 | 1513 / 6809 / 4.5 | 1549 / 7072 / 4.57 |
| L4 | 141 / 305 / 2.16 | 117 / 249 / 2.13 |
| 合计 | 3,762 / 15,438 / 4.10 | 3,834 / 17,033 / 4.44 |

- L0→L1 单次平均输入 SST 一致（10.6 vs 10.4，最大 21 vs 16）——由 L0 小文件合并特性决定；
- 深层（L1→L2/L2→L3）单次平均 3.4-4.6 个，两配置一致；job 数相当——compaction 行为由数据与
  LSM 参数驱动，与写线程数基本无关。

## 5. 结论

1. **写线程数 16→8 不改变停顿结构**：memtable stop 仍占运行时间 ~94%（2,605 vs 2,595 次），
   L0/pending-bytes 停顿仍为 0——瓶颈在后台 compaction 消费能力（不变），不在写线程数；
2. **吞吐仅降 10%**（13,978 → 12,558 ops/s）：写线程近乎全程停顿，有效写入由 compaction 出清节奏决定；
3. **写放大与 compaction 规模与线程数无关**（9.8× vs 10.0×、L0→L1 平均 10.6 vs 10.4 个 SST）——
   均由 workload 分布与 LSM 参数决定；
4. 对 ZeroFlush 的意义不变：原生瓶颈 = 深层 compaction 消费 < flush 生产，memtable 出清为唯一节流阀；
   写线程数只是改变每次停顿的粒度，不改变停顿本身。
