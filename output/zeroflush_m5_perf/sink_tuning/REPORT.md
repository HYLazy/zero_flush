# sink / L2 清场受控实验（2026-09-15，实验 A/B）

> ⚠ **2026-09-15 更正（step 0a）**：本报告 A/AB 两臂的"compaction 完成数 0"
> 已定位为一个真实 bug——窄下沉把区间 `Slice` 指向了已释放的 `std::string`
> （heap-use-after-free，glibc tcache 覆写了 16B key 的前 16 字节），picker
> 收到的是垃圾边界。**A/AB 两臂的数据与"结论一"作废**（其中 21 次 trivial
> move 属偶发）；B 臂（整分区 + 调清场阈值）不经过该路径，结论二仍成立。
> 修复后的窄下沉分类与写放大结果见 **REPORT_0A.md**。

> 目的：压缩 ZF 的 →L2（sink）+ →L3（L2 清场）写入量（50GB 下 649–921GB）。
> 规模：48M 键空间 / 16 线程 × 1M 写 = 16M 写（14GB DB），单臂约 1–7 分钟。
> 开关（本提交新增，env 门控，默认行为不变）：
> - `ZF_SINK_WHOLE_RANGE=1`：旧行为（每次下沉整个分区区间）；
>   默认 = 按"分区内最左 L1 文件的键区间"下沉，剩余区间重新入队（实验 A）。
> - `ZF_SINK_L2_CLEAR_MB=N`：L2 清场阈值（默认 4096MB）。

## 2. 结论一：A 臂实现不完整，但暴露了关键机会

A/AB 臂 **compaction 完成数为 0**：`CompactRange(1→2, 窄区间)` 绝大多数
构造失败（失败日志是 `ROCKS_LOG_DEBUG`，INFO 级别下静默，故未在 LOG 中）。
后果：下沉基本没执行，数据留在 L1（140 文件），吞吐 21–25 万 ops/s 是
"没做下压工作"的假象 —— **A 臂当前不是有效配置**。

但 A 臂中**成功构造的那部分下沉全是 trivial move**：
`EVENT_LOG` 统计 21 次 `trivial_move`、0 次 `compaction_started/finished`，
而 base 臂是 245 次真 compaction + 2,463 次文件创建/2,493 次删除。
即：**当下沉区间收窄到单个 L1 文件的键域、且 L2 在该区间无重叠文件时，
下沉退化为"把文件搬到 L2"（零重写）**。这正是 M5 设计"每 range ≤64MB
单文件、满即下沉"想要的形态，也是把 649–921GB 压下来的唯一现实路径。

## 3. 结论二：只调 L2 清场阈值是"搬移成本"，不是减少成本

B 臂（4GB→8GB）：
- L2 清场次数 347 → **155**，**→L3 从 41.1G 降到 10.3G（−75%）**（预期方向）；
- **但 →L2 从 64.8G 涨到 109.2G（+69%）** —— L2 容量大了，下沉归并的
  重叠面随之变大；
- 总量 105.9G → **119.5G（更差 −13%）**，吞吐 38.7K→43.4K（+12%，但
  compaction 总输出增加）。

**判定**：提高 L2 清场阈值单独使用会把成本从 L3 搬到 L2，不减少总重写。
必须与"下沉粒度收窄"（结论一）联合，否则不采用。

## 4. 下一步（按收益排序）

1. **把 A 修正为真正有效的"按 range 下沉"**：
   - 修掉 `CompactRange` 构造失败（逐条打点失败原因：being_compacted /
     range 无重叠 / picker 语义），确保每个 range 都能下沉；
   - 下沉区间 = 单个 L1 文件的键域（而非分区全域）→ 期望大部分下沉
     变成 trivial move（零重写）或 ≤2 文件的归并（有界重写）；
   - 验收指标：→L2 + →L3 从 105.9G(base) 降到接近 native 的量级。
2. **随后再叠加 B**（L2 清场阈值）——在 range 化下沉成立后，L2 的驻留
   与重叠结构会不同，阈值的作用需要重测。
3. 实验 C/D（sink 与普通 compaction 合并调度、同区间去重）在 1 完成后
   才有意义（当前 sink 构造失败已掩盖了调度层面的重复）。
4. 实验 E（并发参数）留待写放大下降后再做——用户判断正确：先降写放大。
