# 50GB merge-ON 验收（zf_install_mu_ 修复后，2026-09-12）

> 目的：在真实 50GB 负载上验证 M4.9 并发崩溃修复（commit 2980464），并量化
> 安装锁的实际代价。
>
> 配置：16 线程 / 1KB 值 / 48M 键空间 / sampled + 16 分区 / `zf_base_merge=true`
> （merge ON）/ governance OFF / `ZF_L0_TRIGGER=1e8`（不触发 L0 文件数项）/
> compression=none / bg=24 / subcompactions=16。
> 写入量：`--num=3000000`（每线程）→ 16 线程 = **48M ops = 48GB 用户数据**
> （每键一次写，无覆盖）。

## 1. 主结果（锁开启，默认）

| 指标 | 结果 |
|---|---|
| **fillrandom** | **327,460 ops/s**（146.6s，324.8 MB/s）；对照臂 fill 时 `rc=0` 无错误 |
| **readrandom** | 77,093 ops/s（1,660s），**8,000,000 / 8,000,000 found（100%）** |
| 数据完整性 | **零 corruption / 零 overlapping 报错；8M 随机采样全部命中** |
| 崩溃 | 无（M4.9 曾在此配置 100% 崩溃） |
| 让位（install lock busy） | **0 次**（本次负载未触发锁竞争） |
| LSM 终态 | L0=3 / L1=19 / L2=57 |
| 物理形态 | SST 0.4GB（52 文件）+ WAL 47.3GB（2,157 文件） |

## 2. 安装锁代价（配对 A/B，同键空间同参数）

同一二进制，仅 `ZF_INSTALL_LOCK` 不同：

| 臂 | fill 吞吐 | 墙钟 | DB 终态 | 物理形态 |
|---|---|---|---|---|
| **锁开启（默认）** | **317,962 ops/s** | 151.0s | 48GB | SST 0.4GB + WAL 47.3GB |
| 锁关闭（`ZF_INSTALL_LOCK=0`） | **76,779 ops/s** | 625.2s | 3.7GB | SST 3.6GB + WAL ~0 |

**结论：在这个负载上，锁开启比锁关闭快 4.1×，不是慢。** 先前在
`zf_govern_bench`（256 分区 / 8M 键 / 高 churn / 2M 写）上测到的 1.9× 变慢
**不能外推到 50GB merge-ON 负载**——两者的批并发、churn 与 L0/L1 形态不同。

两臂的物理形态差异是解读关键：
- **锁开启**：数据大量留在分区 WAL（47.3GB），只有 0.4GB 落到 SST——ZF 的
  "值在 WAL、SST 存 locator"设计让写入路径几乎不产生合并开销；
- **锁关闭**：fill 期间发生 **764 次原生 compaction**，把数据反复合并回 SST
  （终态 3.6GB SST、WAL 基本清空），总物理写入远大于锁开启臂，故更慢。

即：锁关闭时原生 compaction 在写路径上持续"消费"L0/L1，引发额外读写；
锁开启让 ZF 批次串行规划后，原生 compaction 不再被频繁触发（本次 0 次）。

## 3. 与历史基线对照（**口径不同，不可直接比**）

| 来源 | fill 吞吐 | 键空间/写入量 | 备注 |
|---|---|---|---|
| 本次（锁开） | **327K ops/s** | 48M 键 / 48M 写（1× 覆盖） | 终态 48GB（WAL 47.3GB + SST 0.4GB） |
| 本次（锁关） | 77K ops/s | 同上 | 终态 3.7GB（SST 3.6GB + WAL ~0） |
| 09-02 cmp_1kb50（merge ON，旧代码） | 27,066 ops/s | 48M 键 / 768M 写（16× 覆盖） | 不同写入量/覆盖率 |

**不可直接比较的原因**：09-02 的 `--num=48000000` 是**每线程**写 48M 次，
16 线程共 768M 次（16× 覆盖）；本次 `--num=3000000` 共 48M 次（1× 覆盖）。
覆盖率差异会显著改变合并成本。若要严格对照，需要用 `--num=48000000` 重跑
（768M ops，预计 40–60 分钟）。

## 4. 需要跟进的异常：WAL 未物化

本次验收通过（数据完整、可读），但物理形态暴露一个独立问题：
**fill 完成后 47.3GB 数据仍在分区 WAL，SST 只有 0.4GB**——ZF 物化管线在
本负载下没有把数据从 WAL 搬进 SST。同时：
- `ZFDBG-install` 只记录 68 次安装（48 L0 + 20 L1），对 48M 写/16 分区
  而言极低；
- 原生 compaction 0 次（锁开启臂）；
- read 阶段 8M 全命中说明数据可读（locator 指向 WAL），但 read 吞吐只有
  77K ops/s（历史同量级为 188K）——与"值仍在 WAL、每次读要回 WAL 取"
  的形态一致。

判断：**这属于"物化/回收滞后"而非崩溃或丢数据**，但会让读性能退化、
WAL 空间不回收。建议专项核查：① 该负载下 `kDirect/kMergeBase/kSkip` 的
决策分布（为何 install 只有 68 次）；② WAL 是否有回收水位被滞后推进的
迹象（`zfwal` 文件数 2,157 而分区只有 16 个）。

## 5. 结论

1. **M4.9 修复在 50GB merge-ON 负载上工作正常**：无崩溃、无 corruption、
   8M 随机采样全命中；让位 0 次说明本次负载未触发锁竞争。
2. **安装锁的吞吐代价在目标负载上未出现**（反而快 4.1×，机制见 §2），
   之前 1.9× 的测量不能外推。**可以继续用锁开启作为默认。**
3. **新发现一个与并发无关的问题**：merge-ON 50GB 下物化严重滞后（数据大
   量滞留 WAL）。这是下一轮要查的对象，不影响本次崩溃修复的结论。
