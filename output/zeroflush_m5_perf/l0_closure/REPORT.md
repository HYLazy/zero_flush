# L0→L1 闭包分布实验报告（2026-09-12）

> 目的：用实测回答"提高 L0 触发阈值能否减少总重写"（v1.1 方案的核心假设），
> 并钉死"每次 L0→L1 compaction 的真实成本由什么决定"。
>
> 方法：`db_bench fillrandom`，唯一变量 = `ZF_L0_TRIGGER`
> （`level0_file_num_compaction_trigger`），采集 DB LOG 的
> `compacted to:` 完成行（含 `MB in(non_output, output_level)`、
> `out(MB)`、`files in(a,b)`、目标层、write-amplify），无需改代码。

## 0. 结论（三段）

1. **L0 触发阈值不是杠杆。** 把 trigger 从 1e8 改成 4，事件总数几乎不变
   （126 → 116），但**输入字节从 6.9GiB 涨到 22.1GiB、输出从 3.75GiB 涨到
   16.9GiB**——降低阈值不但没减少重写，还因为引入 intra-L0 compaction
   与更密集的 L0→L1 事件而恶化。
2. **真正的成本变量 = L1 驻留切片。** 一次 L0→L1 事件的输入闭包 ≈
   「1 个 L0 文件 + 该键域覆盖的全部 L1 文件」，其规模随 L1 在该分区的
   驻留字节单调增长。四臂实测：
   | 臂 | L1 驻留 | 闭包 p50 | 闭包 max | 输出/用户 |
   |---|---|---|---|---|
   | 小规模 16 分区 | 50MB | 48MB | 311MB | 0.49× |
   | 中规模 16 分区 | ~100MB | 85MB | 315MB | 1.06× |
   | 中规模 16 分区（trigger=4） | ~85MB | 110MB | 749MB | 2.22× |
   | 中规模 **4 分区** | ~840MB | **261MB** | 497MB | **2.02×** |
3. **这解释了 50GB 运行的 52×。** 50GB 时 L1 驻留 9.9GB（约 620MB/分区，
   峰值更高），闭包相应涨到 GB 级（实测最大单次 2.98GB / 305 万条），
   于是每次 25MB 的新数据都要重写数百 MB 的 L1。

## 1. 实验设计

| 臂 | 规模 | 分区 | `ZF_L0_TRIGGER` | 总 ops | 用户字节(A) |
|---|---|---|---|---|---|
| A | 250K 键 | 16 | 1e8（默认） | 8M | 7.63 GiB |
| B | 250K 键 | 16 | 4 | 8M | 7.63 GiB |
| M-1e8 | 4M 键 | 16 | 1e8 | 16M | 15.26 GiB |
| M-4 | 4M 键 | 16 | 4 | 16M | 15.26 GiB |
| P4 | 4M 键 | **4** | 1e8 | 32M | 30.5 GiB |

固定：16 线程、1KB 值、sampled 路由、merge 关闭、治理关闭、compression=none、
`max_background_jobs=24`、`subcompactions=16`、每臂独立干净 DB。
（注意 `--num` 是**每线程** op 数，总 ops = num × threads。）

## 2. 核心观测

### 2.1 阈值杠杆：无效且方向为负

| 指标 | A（trigger=1e8） | B（trigger=4） | 变化 |
|---|---|---|---|
| 事件总数 | 126 | 116 | −8% |
| 输入合计 / 用户 | 0.91× | **2.90×** | **3.2×** |
| 输出合计 / 用户 | 0.49× | **2.22×** | **4.5×** |
| 闭包 p50 | 47.7MB | 109.9MB | 2.3× |
| 闭包 max | 310.8MB | 749.1MB | 2.4× |

B 臂多出 **38 次 intra-L0 compaction**（`level 0, files in(0, N)`，输出仍在
L0），把多个小 L0 文件合并成大文件——纯额外写放大，与 L0→L1 事件叠加。
即：`trigger=4` 并没有"把大事件切小"，而是增加了事件种类与总量。

### 2.2 闭包 = L1 驻留切片（规模依赖）

- 小规模：L1 终态 21 文件 / 50MB → 闭包 p50 47.7MB，`files in(6,1)`
  （6 个 L0 + 1 个 L1 文件），输出 27–34MB，`write-amplify 0.4–0.5`。
  因为 250K 键全域热点、大量覆盖被丢弃，闭包与输出都小。
- 中规模：L1 28–100MB → 闭包 p50 85MB，`write-amplify` 上升到 0.8 左右。
- **P4（4 分区）**：单分区承载 1M 键（≈1GB live），L1 驻留 840MB，
  闭包 p50 **261MB**、出现 497MB 的单次事件，L2 也被填起来
  （终态 L2=62 文件），输出/用户 **2.02×**。

### 2.3 每事件的写放大（per-event WA）

P4 臂的典型事件：`MB in(564, 3) out(507)` → write-amplify ≈0.9，即读入 567MB
写出 507MB。对照 50GB 运行的实测单次最大 2.98GB——同一条曲线上的不同规模点。

### 2.4 ZF 侧安装

| 臂 | ZF L0 安装 | 平均文件 | 安装/用户 | ZF L1 安装 |
|---|---|---|---|---|
| A | 344 次 / 5.24GiB | 15.6MB | 0.69× | 16 次 / 50MB |
| M-1e8 | 664 次 / 12.8GiB | 19.7MB | 0.84× | 16 次 / 56MB |
| P4 | — | — | — | — |

安装体积随规模温和增长（0.69→0.84×），**不是** 4TB 的主要来源；
主要来源是原生 compaction 的重复重写。

## 3. 对 P1 根因的修正

原 `ZEROFLUSHV0_PROBLEM_STUDY.md` 的判断需要据此更新：

| 原判断 | 实测修正 |
|---|---|
| "L0 无 ZF 消费路径，数据只能靠原生层间归并消化" | 原生 L0 消费**始终在运行**：字节项 `total_size / max_bytes_for_level_base` 使 L0 达到 1GB 即可触发 L0→L1（version_set.cc:3914） |
| "抬高 L0 分母可减少重写"（v1.1 假设） | **不成立**：事件数不受阈值主要控制，且 per-event 闭包由 L1 驻留决定 |
| "整分区重写" | 更准确：**闭包 = 该 L0 文件键域覆盖的全部 L1 文件**；在 50GB 规模下 L1 驻留 620MB–3GB/分区，故每次事件接近整分区 |

**新的因果链**：
```
数据持续写入 → L0 累积至 1GB（字节 score 触发）
  → L0→L1 事件：挑 1 个 L0 文件 + 其键域内全部 L1 文件
  → 闭包大小 ∝ L1 在该分区的驻留字节
  → L1 驻留又因 L1→L2 跟不上而持续增长（50GB 时 9.9GB vs 1GB 目标）
  → 每次事件接近整分区重写 → 52× 写放大
```

## 4. 修复方向（按证据排序）

1. **限制/管理 L1 驻留**是真正的杠杆：
   - 架构目标是 `每 range ≤64MB 单文件`。当前 L1 是"每分区累计多文件"
     （50GB 时 140 文件/分区约 8.75 文件），单分区驻留 620MB–3GB。
   - 让 ZF 在 L1 保持每 range 单文件、满即下沉 L2，使 L1 驻留恒 ≤ 目标值。
2. **不要动 L0 触发阈值**（本次实验证伪其收益，且降低会引入 intra-L0 写放大）。
3. `ZF_MAX_L1_BYTES` 不是可用杠杆：它同时抬高 L0 字节阈值与 L1 容量目标，
   无法单独控制 L1 驻留（本次实验未再测该共享参数，v1.1 §2.1 的判断成立）。

## 5. 局限与后续

- 负载为覆盖型（churn 16×/4×/1×），与 50GB 运行的"唯一键一次写"不同；
  覆盖率高会低估输出量（大量记录被丢弃）。P4 臂（4 分区）最接近目标规模
  的机制形态，但闭包仍未达到 50GB 的 GB 级。
- 若要复现 GB 级闭包，需单分区 live ≥ 数 GB：建议下一步用
  **4 分区 × 16M 键 / 64GB 写**（约 5–10 分钟）验证闭包是否按比例增长到
  1–3GB，并同时验证"L1 驻留上限"是否能压住闭包。
- 本文所有数字可由 `results/*.LOG` 重放：`python3 parse_closure.py results`。
