# L0→L1 闭包分布实验报告（2026-09-12）

> 目的：用实测回答"提高 L0 触发阈值能否减少总重写"（v1.1 方案的核心假设），
> 并钉死"每次 L0→L1 compaction 的真实成本由什么决定"。
>
> 方法：`db_bench fillrandom`，唯一变量 = `ZF_L0_TRIGGER`
> （`level0_file_num_compaction_trigger`），采集 DB LOG 的
> `compacted to:` 完成行（含 `MB in(non_output, output_level)`、
> `out(MB)`、`files in(a,b)`、目标层、write-amplify），无需改代码。

## 0. 结论（三段）

> **勘误（2026-09-12 晚，v1.2 评审后自查）**：本报告初版表格中 M-4 臂一行
> 误抄为 B 臂数值（116 事件 / 2.90× / 2.22×）。实测 M-4 为 **204 事件 /
> 4.67× / 3.89×**，且闭包 p90 达 1.23GB。修正后"闭包只由 L1 驻留决定、
> 与 L0 侧无关"的结论**不成立**：闭包同时受 L0 输入大小影响，而 L0 输入
> 大小又被 trigger 通过 intra-L0 合并显著改变（见 §2.2）。修正后的结论如下。

1. **L0 触发阈值是负向杠杆，不是优化杠杆。** 4M 键域下把 trigger 从 1e8
   降到 4：事件数 262→204，但**输入 22.9→71.7GiB、输出 16.2→59.4GiB
   （×3.7）**，闭包 p90 从 96MB 涨到 1.23GB。代价来自两处：多出 77 次
   **intra-L0 compaction**（L0 内部重写 7.29GiB），以及这些合并把 L0 输入
   从 ~21MB/文件放大到 ~200MB+/文件，连带把 L0→L1 闭包整体推高。
2. **闭包 = f(L0 输入大小，L1 重叠驻留)。** 实测 L0→L1 单事件输入闭包：

   | 臂 | L0 输入 p50 | 闭包 p50 | 闭包 p90 | 闭包 max | L0→L1 输出/用户 |
   |---|---|---|---|---|---|
   | A（250K 键/16 分区/1e8） | ~17MB | 48MB | 67MB | 311MB | 0.49× |
   | M（4M 键/16 分区/1e8） | ~21MB | 85MB | 96MB | 315MB | 1.06× |
   | B（250K 键/16 分区/4） | ~100MB | 101MB | 685MB | 749MB | 1.84× |
   | M-4（4M 键/16 分区/4） | ~200MB | 146MB | 1230MB | 1321MB | 3.41× |
   | P4（4M 键/**4 分区**/1e8） | ~150MB | **417MB** | 608MB | 1361MB | 2.77× |

   两个自变量都推高闭包：L0 侧（trigger 越低、intra-L0 合并越多，单个 L0
   输入越大）与 L1 侧（分区越大/L1 驻留越高，重叠 L1 越多）。**P4 与 M-4
   的对比最关键**：两者 L0 输入量级相近（~150–200MB），但 P4 的分区承载
   1GB live 而 M 只有 250MB live → P4 闭包 p50 是 M-1e8 的 4.9 倍。
3. **50GB 的 4TB 与这些点同源。** 50GB 运行 L1 驻留 9.9GB（L1 峰值 533 文件）、
   单次 compaction 最大 2.98GB——量级上延续 P4 的趋势（分区 live 更大）。

## 1. 实验设计

| 臂 | 键域 | 分区 | `ZF_L0_TRIGGER` | 总 ops | 用户写入(A) |
|---|---|---|---|---|---|
| A | 250K | 16 | 1e8（默认） | 8M | 7.63 GiB |
| B | 250K | 16 | 4 | 8M | 7.63 GiB |
| M-1e8 | 4M | 16 | 1e8 | 16M | 15.26 GiB |
| M-4 | 4M | 16 | 4 | 16M | 15.26 GiB |
| P4 | 4M | **4** | 1e8 | 32M | 30.5 GiB |

固定：16 线程、1KB 值、sampled 路由、merge 关闭、治理关闭、compression=none、
`max_background_jobs=24`、`subcompactions=16`、每臂独立干净 DB。
（注意 `--num` 是**每线程** op 数，总 ops = num × threads。）

**注意**：键域与写入量是两件事——A/B 臂键域 250K、写入 8M 次（16× 覆盖），
M 臂键域 4M、写入 16M 次（4× 覆盖），P4 键域 4M、写入 32M 次（8× 覆盖）。
覆盖率高会低估输出（大量记录在归并中被淘汰）。

## 2. 核心观测

### 2.1 阈值杠杆：k=4 使成本上升约 3.7×

| 指标（4M 键域） | M-1e8 | M-4 | 变化 |
|---|---|---|---|
| 事件总数 | 262 | 204 | −22% |
| 其中 intra-L0（输出到 L0） | 0 | **77** | — |
| L0→L1 事件 | 262 | 127 | −52% |
| L0→L1 输入 / 用户 | 1.50× | **4.67×** | 3.1× |
| L0→L1 输出 / 用户 | 1.06× | **3.41×** | 3.2× |
| 闭包 p50 | 85MB | 146MB | 1.7× |
| 闭包 p90 | 96MB | **1230MB** | **12.8×** |
| 闭包 max | 315MB | 1321MB | 4.2× |

intra-L0 把多个小 L0 文件合并成大文件（`files in(0,N)`，输出仍 L0），
单这一项就重写 7.29GiB；而它同时抬高了后续 L0→L1 的 L0 侧输入，
使每次事件的闭包与输出翻倍。

### 2.2 闭包的两个自变量（分层分解）

| 臂 | intra-L0（输出到 L0） | L0→L1 | 更深层 |
|---|---|---|---|
| A | — | 126 次 / 输入 6.91GiB / 输出 3.75GiB | — |
| B | 38 次 / 输入 2.90GiB / 输出 2.90GiB | 78 次 / 19.24 / 14.01GiB | — |
| M-1e8 | — | 262 次 / 22.87 / 16.18GiB | — |
| M-4 | 77 次 / 7.29 / 7.29GiB | 127 次 / 63.95 / 52.11GiB | — |
| P4 | — | 127 次 / 58.26 / 42.33GiB | L2→L3 206 次 / 27.87 / 19.18GiB |

（intra-L0 的输入=输出，是纯内部重写，不减少任何 L1 驻留。）

### 2.3 ZF 侧安装

| 臂 | ZF L0 安装 | 平均文件 | 安装/用户 | ZF L1 安装 |
|---|---|---|---|---|
| A | 344 次 / 5.24GiB | 15.6MB | 0.69× | 16 次 / 50MB |
| M-1e8 | 664 次 / 12.8GiB | 19.7MB | 0.84× | 16 次 / 56MB |

安装体积随规模温和增长（0.69→0.84×），**不是** 4TB 的主要来源；
主要来源是原生 compaction 的重复重写。

## 3. 对 P1 根因的修正

| 原判断 | 实测修正 |
|---|---|
| "L0 无 ZF 消费路径，数据只能靠原生层间归并消化" | 原生 L0 消费**始终在运行**：字节项 `total_size / max_bytes_for_level_base` 使 L0 达到 1GB 即可触发 L0→L1（version_set.cc:3914） |
| "抬高 L0 分母可减少重写"（v1.1 假设） | 未直接测（`ZF_MAX_L1_BYTES` 是共享参数）；但**降低文件数 trigger 实测使成本 ×3.7**，方向为负 |
| "闭包只由 L1 驻留决定"（本报告初版） | **不成立**：闭包 = f(L0 输入大小, L1 重叠驻留)；L0 输入大小受 trigger 与 intra-L0 合并强烈影响 |
| "整分区重写" | 更准确：**闭包 = 该 L0 输入键域覆盖的全部 L1 文件**；50GB 规模下 L1 驻留 620MB–3GB/分区，故每次事件接近整分区 |

**新的因果链**：
```
数据持续写入 → L0 累积（字节 score 主导，1GB 触发）
  → picker 挑 1 个 L0 文件 + 其键域内全部 L1 文件
  → 闭包 = L0 输入 + L1 重叠驻留（两者共同决定）
  → L1 驻留又因 L1→L2 被 skipped_l0_to_base 压制而持续增长
  → 每次事件接近整分区重写；intra-L0 会进一步放大 L0 侧输入
  → 50GB 规模下 52–84× 写放大（取决于分母口径，见 §5 表注）
```

## 4. 修复方向（按证据排序）

1. **限制/管理 L1 驻留**是主杠杆：
   - 目标：L1 保持"每 range ≤64MB 单文件、满即下沉"，使任一 L0 输入的
     重叠 L1 面有界。当前实测 L1 驻留 620MB–3GB/分区（50GB 运行）。
   - 配套：L1→L2 的推进不能被 L0 持续压制（`skipped_l0_to_base`，
     compaction_picker_level.cc:212-217 的置位条件需先审计）。
2. **不要动 L0 文件数 trigger**：k=4 实测使成本 ×3.7，且引入 intra-L0 重写。
3. `ZF_MAX_L1_BYTES` 是共享参数（同时改 L0 字节阈值与 L1 目标），
   不能单独控制 L1 驻留；如需隔离实验要单独加补丁。

## 5. 表注与口径（回应 v1.2 §1.3）

1. **键域 vs 写入量**已按上表分开列出（A/B：键域 250K、写 8M 次；
   M：键域 4M、写 16M 次；P4：键域 4M、写 32M 次）。
2. **B 与 M-4 是独立测量**，各自 LOG 在 `results/B_trig4.LOG` 与
   `results/M_trig4.LOG`；初版表格误抄导致两者数值相同，已修正。
3. **闭包口径**：本文闭包 = L0→L1 事件的输入字节**全部**（L0 输入 + 目标层
   输入），已按 `level=1 且 files in(a>0, b)` 过滤；intra-L0 单列。
4. **52×/83.7×/93.7×**：三者分母不同——83.7× = 原生 compaction 累计输出
   4,019.6GB ÷ 用户数据 48GB；93.7× = SMART 设备写入 4.57TB ÷ 48GB；
   52× = 同一次运行的 ZF 侧物化/用户口径（该值口径需以原报告为准重算，
   本文不宣称三者可直接比较）。

## 6. 局限与后续

- 覆盖率高（4–16×）会低估输出（记录在归并中被淘汰）；M-4 与 P4 的绝对值
  不能直接外推到 50GB 的"唯一键一次写"。
- 若要复现 GB 级闭包且覆盖率接近 1×：建议 **4 分区 × 16M 键 × ~64GB 写
  （覆盖 ~4×）**，预期闭包 p50 达 GB 级；随后加"L1 驻留上限"补丁复测
  同一负载，直接检验 H1.1（限制驻留）的收益。
- 本文所有数字可由 `results/*.LOG` 重放：`python3 parse_closure.py results`
  （分层分解另见 `results/ANALYSIS.txt`）。
