# L0→L1 闭包分布实验报告（2026-09-12）

> 目的：用实测回答三个问题——① L0 触发阈值是不是优化杠杆；② 单次 L0→L1
> 事件的成本由什么决定；③ 50GB 运行里 3GB 级重写是怎么来的。
>
> 方法：`db_bench fillrandom`，采集 DB LOG 的 `compacted to:` 完成行
> （`MB in(non_output, output_level)`、`out(MB)`、`files in(a,b)`、目标层、
> write-amplify）。无需改代码。解析器 `parse_closure.py`。

## 0. 结论

1. **L0 触发阈值不是优化杠杆，是负向杠杆。** 4M 键域下 trigger 1e8→4：
   L0→L1 输出/用户 1.06×→3.41×（×3.2）；1 分区下 0.87×→1.97×（×2.3）。
   机制：阈值只改变**事件频率**，而每次事件仍要拉入全部 L1 重叠；
   降低阈值 = 让同一批 L1 驻留被重写更多次（不改变单次闭包）。
   4M 键域下还会额外引入 77 次 **intra-L0 compaction**（纯内部重写）。
2. **单次闭包 = L0 输入 + 该键域的 L1 驻留，后者是主导项。** 实测：

   | 臂 | 分区 | 键域 | 覆盖 | L0→L1 闭包 p50 | L1 输入 p50 | L1 输入 max | 输出/用户 |
   |---|---|---|---|---|---|---|---|
   | A | 16 | 250K | 16× | 48MB | — | — | 0.49× |
   | M-1e8 | 16 | 4M | 4× | 85MB | — | — | 1.06× |
   | B | 16 | 250K | 16× | 101MB | — | — | 1.84× |
   | M-4 | 16 | 4M | 4× | 146MB | — | — | 3.41× |
   | P4 | 4 | 4M | 8× | 417MB | — | — | 2.77× |
   | H16 | 4 | 16M | 1× | 344MB | 246MB | 256MB | 1.05× |
   | **H2** | **1** | 16M | 1× | **2075MB** | **1006MB** | 1006MB | 0.87× |
   | H2t4 | 1 | 16M | 1× | 1481MB | 1006MB | 1006MB | 1.97× |
   | 50GB 运行 | 16 | 48M | 1× | — | — | — | ~52–84×（口径见 §5） |

   闭包随**分区承载的数据量**（= 该范围 L1 驻留）单调放大：16 分区时
   单分区 live 250MB–1GB → 闭包 85–417MB；**1 分区时单分区 live 16GB →
   闭包 2075MB，其中 1006MB 是从 L1 读入的旧数据**。
3. **H2 复现了 50GB 的机制。** H2 的 L1 输入恰好被 `max_bytes_for_level_base=1GB`
   钉在 1006MB（单分区 L1 ≤ 1GB 目标），闭包 2GB——与 50GB 运行的单次最大
   2.98GB / 305 万条同一量级、同一机制。**50GB 时 L1 驻留 9.9GB（峰值 533
   文件）时闭包接近整分区，由此产生 4TB 级重写。**

| 臂 | 键域 | 分区 | `ZF_L0_TRIGGER` | 总 ops | 用户写入(A) | 覆盖 |
|---|---|---|---|---|---|---|
| A | 250K | 16 | 1e8 | 8M | 7.63 GiB | 16× |
| B | 250K | 16 | 4 | 8M | 7.63 GiB | 16× |
| M-1e8 | 4M | 16 | 1e8 | 16M | 15.26 GiB | 4× |
| M-4 | 4M | 16 | 4 | 16M | 15.26 GiB | 4× |

## 2. 核心观测

### 2.1 阈值：只改频率，不改单次成本（H2 vs H2t4，1 分区对照）

| 指标 | H2（trig=1e8） | H2t4（trig=4） | 变化 |
|---|---|---|---|
| L0→L1 事件 | 14 | 33 | 2.4× |
| intra-L0 事件 | 0 | 0 | — |
| **L1 输入 p50** | **1006MB** | **1006MB** | **不变** |
| L0 输入（均值≈闭包−L1） | ~1070MB | ~475MB | −56% |
| 闭包 p50 | 2075MB | 1481MB | −29% |
| **输出/用户** | **0.87×** | **1.97×** | **2.3×** |

同一次事件里 L1 输入恒为 1006MB（= 单分区 L1 驻留，被 1GB 目标封顶），
说明**闭包的主导项是 L1 侧，与阈值无关**；阈值降低只是把同一份 L1 驻留
被重写的次数从 14 次提到 33 次 → 总成本 ×2.3。

### 2.2 闭包随分区承载量放大（H16 vs H2）

| 指标 | H16（4 分区） | H2（1 分区） |
|---|---|---|
| 单分区承载 live | 4GB | **16GB** |
| L1 文件数（终态） | 39 | 16 |
| L1 输入 p50 / max | 246MB / 256MB | **1006MB / 1006MB** |
| 闭包 p50 / max | 344MB / 1244MB | **2075MB / 2076MB** |
| 输出/用户 | 1.05× | 0.87× |

单分区从 4GB 涨到 16GB → L1 输入从 246MB 涨到 1006MB → 闭包从 344MB
涨到 2075MB。**闭包与单分区承载量正相关**，这正是"L1 驻留主导"的直接证据。

### 2.3 分层分解（各臂）

| 臂 | intra-L0（到 L0） | L0→L1 | 更深层 |
|---|---|---|---|
| A | — | 126 次 / 输入 6.91GiB / 输出 3.75GiB | — |
| B | 38 次 / 2.90 / 2.90GiB | 78 次 / 19.24 / 14.01GiB | — |
| M-1e8 | — | 262 次 / 22.87 / 16.18GiB | — |
| M-4 | 77 次 / 7.29 / 7.29GiB | 127 次 / 63.95 / 52.11GiB | — |
| P4 | — | 127 次 / 58.26 / 42.33GiB | L2→L3 206 次 / 27.87 / 19.18GiB |
| H16 | — | 67 次 / 27.65 / 15.96GiB | — |
| H2 | — | 14 次 / 24.8 / 13.3GiB | — |

### 2.4 ZF 侧安装

| 臂 | ZF 安装次数 | 落 L0 / L1 | 安装/用户 |
|---|---|---|---|
| A | 360 | 344 / 16 | 0.69× |
| M-1e8 | 680 | 664 / 16 | 0.84× |
| H16 | 483 | 410 / 73 | 0.89× |

ZF 安装体积与用户写入同量级，**不是**写放大的主要来源。

## 3. 修正后的 P1 机制

```
数据持续写入 → L0 累积到字节 score 阈值（total_size / 1GB）→ 触发 L0→L1
  → picker 挑 1 个 L0 文件 + 其键域内全部 L1 文件（compaction_picker_level.cc:816-905）
  → 闭包 = L0 输入 + L1 驻留；L1 侧主导（H2 实测 1006MB，占闭包 48%）
  → L1 驻留因 L1→L2 被 skipped_l0_to_base 压制而持续增长（50GB 运行达 9.9GB）
  → 每次事件逼近整分区重写 → 50GB 累计 4TB（83.7× 输出/48GB）
```

触发公式（`db/version_set.cc:3864-3916`，`level_compaction_dynamic_level_bytes=false`）：

```text
S_L0 = max(num_sorted_runs / level0_file_num_compaction_trigger,
           total_size / max_bytes_for_level_base)
```

`1e8` 只关掉文件数项；字节项以我们给 L1 设的 1GB 为分母 → L0 每 1GB
触发一次。**原生消费始终在运行。**

## 4. 修复方向（按证据排序；§7 已修正第 1 条）

1. **多层 range 局部性（主方向，§7 修正后）**：单独限制 L1 驻留会把成本转移到
   L2（实测输出 0.87×→1.41×，64MB 时 5.28×）。正确目标是**每一层都保持
   "每 range ≤ 目标大小"**（M5 设计即全层约束）。对 48GB/256 分区：
   每分区 ≈187MB，此时闭包上界 ≈187MB；16 分区（每分区 3GB）天然不满足。
2. **修 L1→L2 推进（配合项）**：`skipped_l0_to_base`（compaction_picker_level.cc:216）
   使 base 层候选在 L0 有失败候选时被跳过 → L1 只在 L0 空闲窗口下压。
   先审其置位条件，再做压力下的公平调度。
3. **不要动 L0 文件数 trigger**：两个规模下都是负收益（×2.3 / ×3.2）。
4. **注意 intra-L0**：4M 键域下 trigger=4 引入 77 次纯内部重写（7.29GiB）；
   它是 L0 侧输入膨胀的来源，可与 ① 一起通过"L0 输出尺寸控制"缓解。

## 5. 表注与口径

1. **键域 vs 写入量**分列（见 §1 表）。
2. **B 与 M-4 是独立测量**（`results/B_trig4.LOG` / `results/M_trig4.LOG`）；
   初版误抄已修正（a534fb1）。
3. **闭包口径** = L0→L1 事件的输入字节全部（L0 输入 + 目标层输入），按
   `level=1 且 files in(a>0,b)` 过滤；intra-L0（`level 0`）单列。
4. **52× / 83.7× / 93.7×**：分母不同——83.7× = 原生 compaction 累计输出
   4,019.6GB ÷ 用户数据 48GB；93.7× = SMART 设备写入 4.57TB ÷ 48GB；
   52× = ZF 侧物化口径（待按原报告重算）。**三者不可直接比较。**
5. **覆盖率**：H16/H2 为 1× 覆盖，最接近 50GB 运行形态；A/B、M、P4 为
   4–16×，输出被归并淘汰低估，绝对值不可外推。

## 6. 后续实验建议

1. **在 H2 形态上验证"多层 range 局部性"**：同时限制 L1/L2 的每 range 驻留
   （见 §7.5），观察总输出是否下降而非转移。
2. **或验证大分区数**：256 分区下每分区 live ≈187MB，理论闭包上界随之下降，
   可用同一解析器与 H16（4 分区/344MB）对照。
3. **50GB 复跑 + 解析器**：用同一解析器处理 50GB 运行的完整 LOG，得到
   `intra-L0 / L0→L1 / L1→L2 / L2→L3` 四条路径的实际字节分解，替换
   目前"~52×/83.7×"的混合口径。
4. **H16 的 L1 输入增长轨迹**（54MB→1244MB）值得单独出图，用于验收
   "驻留受控"（v1.2 §4.7）。

## 7. R 实验：限制 L1 驻留（2026-09-12 补测，**负结果，但机制清晰**）

### 7.1 假设与实现

假设（H1.1）：把 L1 驻留目标从 1GB 降到 256MB/64MB，闭包应随之从 2075MB
降到 ~300MB 量级，总写放大下降。

实现：新增实验开关 `ZF_L1_BUDGET_MB`（`db/version_set.cc:CalculateBaseBytes`），
**只覆盖 L1（base level）的层目标**，L0 的字节 score 分母仍用
`max_bytes_for_level_base`（另有既有开关 `ZF_MAX_L1_BYTES` 可固定 L0 阈值）。
负载与 H2 完全相同（1 分区 / 16M 键 / 1× 覆盖 / trig=1e8）。

### 7.2 结果

| 臂 | L1 预算 | L0 阈值 | 事件 | L0→L1 事件 | L1 事件闭包 p50 | L1 输入 p50 | L1 事件输出 | **L2 事件（次/输出）** | 输出/用户 | 吞吐 |
|---|---|---|---|---|---|---|---|---|---|---|
| H2 | 1GB | 1GB | 14 | 14 | 2075MB | 1006MB | 13.30GiB | — | 0.87× | 139K |
| R_budget256 | 256MB | 256MB | 166 | 14 | 1298MB | 229MB | 10.26GiB | 152 / 10.55GiB | 1.36× | 130K |
| **R_iso256** | 256MB | **1GB** | 164 | 14 | 1298MB | **229MB** | 10.26GiB | **150 / 11.32GiB** | **1.41×** | 131K |
| R_budget64 | 64MB | 64MB | 212 | 1 | 1200MB | 61MB | 0.70GiB | 117 / **73.66GiB** | **5.28×** | 82K |

（R_iso256 是隔离臂：L0 阈值显式固定回 1GB，排除 `ZF_L1_BUDGET_MB` 顺带
降低 L0 字节阈值的混杂——两者结果几乎一致，证明混杂不改变结论。）

### 7.3 结论：驻留上限生效，但成本转移到更深的层

1. **L1 侧确实按预期下降**：L1 输入 p50 1006→229MB（256MB 预算）、→61MB（64MB）。
   **驻留上限机制有效。**
2. **但 L1→L2 的代价更大**：256MB 预算下多出 150 次 L2 事件、输出 11.32GiB；
   64MB 预算下 L2 事件输出 **73.66GiB（4.7× 用户数据）**，总输出/用户从
   0.87× 恶化到 5.28×，吞吐 139K→82K（−41%）。
3. **原因**：L2 与 L1 有同样的"宽文件"问题（同一分区的文件互相重叠、覆盖
   整个键域），把数据往下推只是把"每次重写整个范围的 L2 驻留"变成主要成本。
   256MB 预算时 L2 闭包 p50 128MB（尚可）；64MB 预算时 L2 已有 ~2GB 数据
   （16 次 ≈ 每分区 2GB？实测 L2 闭包 p50 725MB），代价按量级放大。

### 7.4 对 H1.1 的修正

**"限制 L1 驻留"不是独立杠杆。** 正确的表述是：

> 需要**每一层**都保持 range 局部性（每 range ≤ 目标大小），否则把数据从
> L1 推到 L2 只是把重写成本转移并放大。2026-09-12 的 50GB 运行（L1 驻留
> 9.9GB、L2 11.9GB）正是"什么都没有界"的形态。

这也解释了 M5 设计（每 range ≤64MB 单文件）为什么是**全层约束**而非仅 L1。
对 48GB 数据、256 个范围而言，每分区 ≈187MB——**在 256 分区下，若各层
都保持每 range 单文件，闭包上界约 187MB，总写放大可回到 ~1× 量级**。
当前 16 分区（每分区 3GB）则天然无法满足该上界。

### 7.5 后续实验建议（修订）

1. **不要把 L1 预算单独收紧**（本次已证伪）。
2. 下一组应验证 **"多层 range 局部性"**：在 4M×4 分区形态下，同时限制
   L1/L2 的每 range 驻留，观察总输出是否下降而非转移。
3. 或直接验证 **256 分区 + 现有 1GB 目标**：每分区 ≈187MB，理论上闭包
   ≤ ~200MB，可用同一解析器与 H16（4 分区/344MB）对照。

1. **在 H2 形态上加"L1 驻留上限"补丁**（每 range ≤64MB 或把
   `max_bytes_for_level_base` 降到分区级），复测同一负载，验证闭包是否
   随之降到 ~128MB 量级。这是 H1.1 的直接检验。
2. **50GB 复跑 + 解析器**：用同一解析器处理 50GB 运行的完整 LOG，得到
   `intra-L0 / L0→L1 / L1→L2 / L2→L3` 四条路径的实际字节分解，替换
   目前"~52×/83.7×"的混合口径。
3. **H16 的 L1 输入增长轨迹**（54MB→1244MB）值得单独出图，用于验收
   "驻留受控"（v1.2 §4.7）。
