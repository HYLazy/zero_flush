# 50GB merge-ON 同窗对照：ZeroFlush vs native RocksDB（2026-09-14）

> 目的：在同机、同盘、同窗口、同参数下对比 ZF 与 native 的 50GB fill/read。
> 参数：`--num=48M`（键空间）`--writes=3M/线程`（16T）= 48M 写；1KB 值、
> compression=none、cache 512MB、bg=24、subcompactions=16、seed=20260914。
> ZF 配置：`e355d35`+`8fb5bab`，merge ON、governance OFF、锁默认开启。
>
> 全部四轮均已完成，DB 大小与键覆盖一致（48M 键空间采样命中 **6,161,212**
> —— 三个引擎逐位一致），可直接比较。

## 3. 差异来源（定位到机制）

| 机制 | native | ZF |
|---|---|---|
| L1→L2（ZF 的 sink 下沉）| 127GB（score 驱动）| **248–476GB（手动 range 下沉）** |
| L2→L3（ZF 的 L2 清场 / native 的层级推进）| 123GB | **401–445GB** |
| sink 次数 | 0 | **4,828 / 7,263** |
| L2 clear 次数 | 0 | **4,674 / 7,166** |

即 **ZF 独有的 sink（L1→L2）+ L2 清场（L2→L3）管线贡献了绝大部分额外写放大**：
- L2 层：ZF 是 native 的 1.9–3.7×；
- L3 层：ZF 是 native 的 3.2–3.6×；
- 因此 fill 吞吐为 native 的 0.34–0.59×。

**ZF 两轮差异也由该管线解释**：无探针臂的 sink/L2clear 次数（7,263/7,166）
高于探针臂（4,828/4,674），compaction 输出相应从 649GB 涨到 921GB，
吞吐从 28.2K 掉到 16.1K。**即 sink 工作量本身不稳定**（同一配置、同负载、
同键空间），这是下一轮要查的对象。

## 4. 读性能（ZF 反超）

| 轮次 | native read | ZF read |
|---|---|---|
| 第一对（16:13 / 17:08）| 798,878 | **901,285**（ZF +13%）|
| 第二对（17:32 / 18:26）| **391,061** | **846,977**（ZF +117%）|

found 三臂一致（6,161,212）。**ZF 读在两对比较中均更快且稳定
（847–901K）；native 第二轮读掉到 391K**（其 DB 596 SST、读阶段可能仍在
后台收敛）。与历史结论一致（100GB E6 矩阵读 0.45–0.96× 反超）。

## 5. 数据完整性（跨引擎一致性）

三臂在 48M 键空间上的命中键数**完全一致**（6,161,212），即写入集与覆盖
率逐位相同；ZF 侧的独立校验（`zf_valcheck`）另确认命中值全部 1024B。
→ **本轮 ZF 与 native 的数据内容等价，性能差异不是数据量差异造成的。**

## 6. 结论与下一步

1. **P1 的剩余差距已量化**：50GB merge-ON 下 ZF fill = native 的
   0.34–0.59×，物理写放大 23–31× vs native 12×；
2. **成本中心是 sink + L2 清场**（ZF 独有路径），而不是物化本身
   （物化输出仅 55GB/1460–1697 次）；
   另外 ZF 读全面反超（+13%~+117%），即差距集中在写路径；
3. **两轮 ZF 波动（28.2K vs 16.1K）与 sink 次数正相关** → 查
   "sink 触发频率为何不稳定"（L1 驻留/L2 阈值/分区局部性）；
4. 下一步建议：把 sink 的**单次下沉范围**与**L2 清场阈值**作为两个变量做
   受控对照（例如 sink 按子区间、L2 清场阈值放大），目标是压缩
   →L2/→L3 的 649–921GB；这与问题文档 §4.1 的 H1.1/H1.2 方向一致。
