# step 0a：窄区间 sink 失败原因分类（2026-09-15）

> 目的：定位"sink/L2 清场受控实验"中窄区间下沉（实验 A/AB）**compaction 完成数为 0**
> 的原因。设计稿 §11 要求先把 request → picked → registered → scheduled →
> installed 打成可观测状态并分类失败原因。
>
> 结论提要：① 原实验 A/AB 臂的"0 次完成"是一个**真实 bug**（use-after-free 把
> 下沉区间指针指向了已释放的 string），不是 picker 语义问题；② 修掉之后窄下沉
> 能正常工作，但**并没有降低写放大**——真实下沉每次只吃 1 个 L1 文件（均 51–53MB，
> 符合 ≤64MB 的设计），却要吃 296–318MB 的 L2 重叠，L2/L1 = 5.8–6.0×；
> 同清场阈值下总 compaction 输出反而比整分区下沉高 14–22%。

## 2. 原实验 A/AB 为什么是 0：`Slice` 指向已释放的 string

`MaybeScheduleZfSink` 窄模式原实现：

```cpp
    if (!zf_sink_whole_range) {
      ...
      const std::string new_lo = best_lo_s;   // ← 内层作用域
      const std::string new_hi = best_hi_s;
      lo = Slice(new_lo);                     // Slice 指向 new_lo 的缓冲
      hi = Slice(new_hi);
    }                                          // ← 字符串在此析构
    begin_storage.SetMinPossibleForUserKey(lo);  // ← 读已释放内存
```

16 字节 key 超过 libstdc++ 的 SSO 上限（15B），`std::string` 走堆分配；析构时
glibc 把 tcache 的 `next`/`key` 两个指针**写在 chunk 的前 16 字节**——正是 key
数据所在位置。于是传给 picker 的区间边界是垃圾数据，绝大多数构造直接落空
（`inputs_empty` 或匹配不到文件），这就是"621 条请求、0 次完成"的来源。

**已修**：`lo_s/hi_s` 提升到循环体作用域，生命周期覆盖 Slice 的全部使用点。
注意 `inputs_empty` 在修复后为 **0**，说明原臂的失败几乎全落在这个原因上——与
UAF 的解释一致。

> 这条修正意味着 `sink_tuning/REPORT.md` 中 **A/AB 两臂的数据与结论 1
> （"窄下沉可退化为 trivial move，是压缩 649–921GB 的现实路径"）不成立**：
> 它是在一个未真正执行的实现上得到的（21 次 trivial move 属偶发）。B 臂
> （整分区 + 调阈值）不经过该路径，结论 2 仍然有效。

## 3. 修复后的分类结果（16M 写 / 14GB，与 base 同参）

| 臂 | 吞吐 | →L2 | →L3 | 合计 | trivial move |
|---|---|---|---|---|---|
| base（整分区 + 4GB 清场，旧数据） | 38,692 | 64.8G | 41.1G | **105.9G** | — |
| **A0a（窄下沉，已修）** | 38,331 | 70.5G (213) | 50.5G (44) | **121.0G** | 89 次 / 6.33G |
| **A0b（窄下沉，已修，含占用者归属）** | 43,071 | 69.6G (193) | 59.7G (50) | **129.3G** | 101 次 / 6.75G |

请求分类（A0b，`taken=2443`）：

```text
pick_ok          284  (11.6%)
expand_clean_cut 1589 (65.0%)   ← 目标 L1 文件被占
no_l1_file        570 (23.3%)   ← 区间内无 L1 文件（多为 requeue 残余）
setup_other         0 ; files_in_compaction 0 ; output_range_overlap 0
占用者归属： sink=1574 (99.1%)  merge=15 (0.9%)
requeue: 右残余 1865 次, 左残余 255 次
```

三条结论：

1. **失败几乎全部是"被另一条下沉占用"**（99.1%），不是被 ZF 融合占用
   （0.9%）。窄下沉总是取分区最左的 L1 文件，一旦该文件的下沉在飞，该分区
   的后续请求就全部失败并 requeue——**自己阻塞自己**。这与设计稿" sink 忙时
   暂缓同范围的新融合，保证消费者取得输入"的假设相反：实践中是 sink 被前一条
   sink 挡住，融合几乎不参与竞争。
2. **窄区间本身是成立的**：真实下沉每次只吃 1 个 L1 文件，平均 51–53MB，全部
   ≤80MB，符合"每 range ≤64MB 单文件"的设计。
3. **写放大不由下沉粒度决定，而由 L2 重叠决定**：每次真实下沉读 51–53MB L1
   却要读 296–318MB L2（**L2/L1 = 5.8–6.0×**），产生约 334MB 输出。把一次
   整分区下沉拆成多次单文件下沉，并没有减少 L2 侧要重写的字节——反而使 L2
   文件更碎，L2→L3 级联更贵（→L3 50.5–59.7G vs base 41.1G）。

对照：每个 L1 文件下沉时，**L2 该区间为空则退化为 trivial move**（零重写）——
两次运行分别有 6.33G/6.75G（约占下沉 L1 字节的 37%）走这条路。这条路径确实
存在，但它只覆盖 L2 空的那部分区间，不足以抵消 L2 重叠带来的重写。

## 4. 对设计稿的影响

> ⚠ **本节两处结论已在第 7 节修正**：① 下方"L2/L1 = 5.8–6.0×"是文本解析配对的
> 假象，按构造出的 compaction 实测为 **≈3.9–4.1×**；② 与"历史 base 105.9G"的
> 比较不可用——同一二进制重跑 base 得 118.0–118.6G（且第三次 85.6G），见第 7 节。

- §11 的验收指标"→L2 + →L3 从 105.9G(base) 降到接近 native 量级"**未达成**：
  同阈值下窄下沉是 121.0–129.3G，比 base **高 14–22%**（两次独立运行一致；
  运行间方差约 7%，方向不受影响）。
- 设计稿把"下沉粒度收窄"当作压缩写放大的唯一现实路径，本实验证伪：**真正的
  杠杆在 L2 的驻留与重叠结构**（以及 L2→L3 级联），不在单次下沉的区间宽度。
- 结论 2（单独调 L2 清场阈值只是把成本从 L3 搬到 L2）不受影响，仍然成立。
- 请求流水本身有 88% 的浪费（11.6% 成功率），其中 23% 是"区间内没有 L1 文件"
  的死请求（左残余 `[r.first, best_lo)` 必然无文件）。这两项是可省的实现开销。

## 6. 后续建议（供设计取舍）

1. **先解释 L2 为何有 5.8–6.0× 的重叠**再谈调粒度：L2 驻留是哪个量级、每个
   range 在 L2 有几个文件、sink 的输出是否落在与输入相同的键区间。若 sink
   输出覆盖范围 > 输入（越界吸附），就会不断制造新的重叠。
2. 若确认"L2 区间非空即必须重写"，则窄下沉的价值只剩 trivial move 那部分；
   应把判据改成"**只对 L2 为空的 range 发起 sink**"（其余 range 走别的路径），
   而不是对所有 range 反复尝试并 requeue。
3. 修请求流水：跳过被占文件取下一个空闲文件；左残余区间不再入队（必然无文件）。

# 7. 第二轮：同一二进制上的三臂对照（2026-09-15 晚）

按用户判断执行：不采用"仅 L2 为空才 sink"，改为**按 L2 重叠成本选择下沉批量**，
并在修复后二进制上重跑整分区基线。命令行：`./run_matrix_0a2.sh`（base2/A0c/B1）
与 `./run_matrix_0a2b.sh`（base2b/B1b/base2c，交错复跑以分离运行顺序与热状态）。

三臂实现：
- `base*`：`ZF_SINK_WHOLE_RANGE=1` —— 请求区间 = 整个分区区间（原行为）。
- `A0c`：默认 —— 取分区内**最左**的 L1 文件，残余区间重新入队。
- `B1`：`ZF_SINK_BATCH=1` —— 种子 = 区间内最左的**未被占** L1 文件，逐个并入相邻
  文件，判据为"合批成本 < 分开成本"：
  `C(separate)=Σ(|A_i|+|O2(A_i)|)`、`C(batch)=|∪A_i|+|O2(∪A_i)|`，
  上限 512MB 输入 / 8 个文件；残余区间仅在"该区间确实还有 L1 文件"时入队。

## 7.2 结论

1. **"6× 重叠"是解析假象，真实是 ≈3.9–4.1×**，且三臂一致。第一轮的 5.8–6.0×
   来自按文本行顺序配对 "Compacting … to L2" 与 "inputs: …"（16 路交织日志会把
   相邻 compaction 的摘要行错配）。以真实 Compaction 输入为准。
2. **合批在本规模下没有发生**：`batch: rounds=282 l1_files=282`，平均 1.0 个
   L1 文件/批——每个分区在 L1 只有约 1–2 个文件，"相邻文件共享 L2 输入"的机会
   不存在，成本判据从未接受并批。因此 **B1 的收益全部来自流水修复而非并批**：
   跳过被占文件使 clean-cut 失败 1500→0，残余检查使请求 2383→643（成功率
   12%→44%），总输出回到与 base 相同（118.2G vs 118.6G）。
   要评估"并批"本身，需要 L1 扇出更高的场景（每分区多个 L1 文件）。
3. **总输出不能直接跨臂比较——存在路径选择混淆**：base 三次运行 118.6 / 118.0 /
   85.6G，末态 L0 = 3 / 38 / 40。落在 L0 的数据（fallback 安装）没被继续下压，
   于是"总输出"变小。只看已排空的运行（L0=3）：base 118.6、B1 118.2、窄下沉
   121.0 / 129.3 / 131.2。**窄下沉比两种整分区方案高 2–11%，但 base 只有 1 次
   已排空样本，方向可信、幅度不可信。**
4. **吞吐：整分区稳定快约 30%**（base 43.7–46.5K vs B1/B1b 32.2–35.4K、A0c 33.5K，
   交错运行复现）。ZF 物化侧累计用时给出旁证：`prof_merge_us` 在窄/合批臂明显
   更高（446s / 372–436s vs base 258–340s），而 `base_merge_count`（265–275）与
   输出字节（22.5–23.7GB）三臂相同——即**下沉策略改变了物化路径的效率**，
   而不是改变了物化的工作量。下沉任务耗时同样偏高：p50 = 1.4s(base) /
   2.3s(A0c) / 3.1s(B1)，均输入字节相近（~350MB）。
5. 99.1% 的"目标文件被占"来自另一条在飞的下沉（A0c）；B1 通过跳过被占文件
   把该失败清零。设计稿"sink 忙时暂缓同范围的新融合"的假设在本工作负载下
   不成立——被挡的从来是 sink 自己。

## 7.3 对设计稿/后续的修正建议

1. **不要把"单文件窄下沉"作为默认优化**（请求与时间成本高、无输出收益）；
   **保留其两个流水修复**（跳过被占文件、残余区间按当前版本检查后再入队）——
   它们与选择策略无关，是纯收益。
2. **"仅 L2 为空才 sink"不予采纳**（同用户判断）：L2 非空时必须有出口，且
   "暂不下沉"只能是有界等待。B1 的形态（合批 + 跳过被占）已经保留了这条出口。
3. **测量口径必须先修**：本轮暴露的最大问题是"固定写量的运行，结束时的未完成
   工作量（L0/fallback 残留）会直接改变总输出"。§15 早已要求"前台窗口与后台
   正常排空后的总时间/总字节分开报告"。建议 harness 在 fillrandom 后追加排空
   阶段（`waitforcompaction` + 等待 ZF pending 归零），并把**末态 LSM +
   install_fallback_l0** 作为每次运行的必须记录项；否则跨臂比较总输出没有意义。
4. **下一步仍应回答 3.9–4.1× 的构成**（用户第 4 点）：单份 L2 文件过宽 / 原生
   输入扩展 / 相邻 sink 重复处理。本轮 `ZFDBG-sink-built` 已记录"请求区间 →
   实际输入范围"，可直接用于判定第二种；第一种需 L2 文件的大小分布（可从
   事件日志统计）；第三种在 L1 扇出低的当前负载下不成立。
5. 并批策略**不建议现在投入**：在 P=16、1KB value、14GB 的规模下每分区只有
   1–2 个 L1 文件，判据无从生效；应先在"每分区多个 L1 文件"的配置下复测，
   再决定是否保留该代码路径。

# 8. 0b-1（排空口径）与 0b-2（3.9× 的构成）

## 8.1 0b-1：默认策略回退 + 排空阶段 + 末态记录（已落地）

代码/脚本改动：

| 位置 | 改动 |
|---|---|
| `MaybeScheduleZfSink` | **默认回到整分区下沉**；`ZF_SINK_NARROW=1`（单文件）/ `ZF_SINK_BATCH=1`（按 L2 重叠合批，含两个流水修复）降级为开关。整分区模式没有残余区间也不做单文件选择，故两个流水修复随 BATCH 保留 |

| `db_bench` 结束 | 新增 `ZF END STATE`：各层文件数 + `num-running-compactions`（配合已有的 `install_fallback_l0`） |
| `run_arm.sh` | benchmark 列表加 `waitforcompaction`（= `DB::WaitForCompact`，等 native 后台与 imm 排空） |

验证（同一二进制，16M 写）：

| 臂 | 策略 | ops/s | 总输出 GB | 末态 LSM | fallback_l0 | drain |
|---|---|---|---|---|---|---|
| base3 | 整分区（新默认）+ 排空 | 41,542 | 127.0 | [3,24,83,171] | 48 | rounds=1, remaining=0, 6.3s |
| A0d | 窄下沉（`ZF_SINK_NARROW=1`）+ 排空 | 30,873 | 129.9 | [3,24,64,177] | 48 | rounds=1, remaining=0, 5.5s |

排空阶段有效：两臂 `HasPendingSealedData()` 均由真转假，`recovery=0`、`skip=0`，说明结束时已无 ZF pending。

## 8.2 0b-2：3.9–4.1× 的构成（三种来源逐一排除）

| 臂 | 文件数 | 合计 | 中位 | p90 | 最大 | <16MB 占比 |

| base2 | 1171 | 68.2 GB | **66.6 MB** | 67.1 MB | 67.7 MB | 7% |
| A0c | 1235 | 70.5 GB | 66.6 MB | 67.1 MB | 67.7 MB | 10% |
| B1 | 1184 | 67.7 GB | 66.6 MB | 67.1 MB | 67.9 MB | 9% |

L2 文件正好落在 64MB 目标粒度上，没有超宽文件。

**(2) clean-cut / SetupOtherInputs 输入扩展？——次要。** 由 `ZFDBG-sink-built`
的"请求区间 → 实际输入区间"（每臂 40 样本；key 是 32 字符 ASCII 十六进制串，

| 臂 | span(in)/span(req)=1.0 | 输入含一个右邻（span≈2×） | 实际 L1 文件数/次 |
|---|---|---|---|
| base2 | 32/37 | 5/37 | 1 个: 32 次, 2 个: 5 次 |
| base2b | 30/37 | 7/37 | 1 个: 31 次, 2 个: 6 次 |
| A0c | 40/40 | 0 | 1 个: 40 次 |
| B1 | 40/40 | 0 | 1 个: 40 次 |

即：**绝大多数下沉只吃 1 个 L1 文件、区间等于请求区间**；只有整分区模式约 14%
的情况会把右邻文件一并拉进来（span ×2）。单文件/合批模式下扩展为零。

**(3) 同一键区间被反复处理？——是主因，且其规模由 L2 驻留决定。**
每个 sink 的 L2 输入实测 200–212 MB，而三个臂的 L2 驻留（末态）为 3.97–5.53 GB
（由 4GB 清场阈值界定），分摊到 P=16 个分区为 **254–354 MB**——与实测的
200–212 MB 同量级。

即：**每个 L1 文件（~50MB）下沉时，要重新归并该 range 在 L2 中驻留的
~200MB 数据**；该 range 在整轮运行中被 ~17 个 L1 文件依次下沉（278 个 L1 文件
/16 分区），于是同一片 ~200MB 区域被反复重写，累计 56 GB L2 读 /14.3 GB L1 读
= 3.9×。

**可检验的推论**：每 sink 的 L2 输入 ≈ `ZF_SINK_L2_CLEAR_MB / P`。B 臂（8GB
清场）→L2 从 64.8G 涨到 109.2G，方向一致。这解释了为什么"调清场阈值"与
"改下沉粒度"是两种不同量级的杠杆：**粒度只影响请求流水，驻留直接影响每次
重写的字节数。**

## 8.3 方法学结论：总输出在固定写量下不可直接跨臂比较

同一策略（整分区）四次运行：**85.6 / 118.0 / 118.6 / 127.0 GB**（±20%）。
窄下沉四次：121.0 / 129.3 / 129.9 / 131.2 GB。合批两次：118.2 / 126.9 GB。

- 排除末态未排空的运行（base2c，末态 L0=40）后：整分区 118.0 / 118.6 / 127.0
  （均值 121.2），窄下沉 121.0 / 129.3 / 129.9 / 131.2（均值 127.9）。
- 方向一致（窄下沉不更低），但**区间重叠**（整分区最高 127.0 > 窄下沉最低 121.0），
  在当前样本量下不足以给出可靠的量化差异。
- 稳定可用的指标是**每次任务的构成**：L1 输入 ~50MB、L2 输入 ~200MB、
  L2/L1 ≈ 3.9–4.0×、下沉后 L1 文件数 1；这些在六个臂之间高度一致。

**建议**：后续比较以"每任务构成 + 末态 + 排空耗时"为主指标，总输出作为
辅助并要求 ≥5 次运行的均值；单次运行的总输出差异（<15%）不应作为结论。

## 8.4 对 0b 后续步骤的直接输入

1. 0b-3（空 edit + ledger 背压）与 0b-4（无 L0 受控实验）的前提不变；本轮
   新增的两条可观测口径（`ZF END STATE`、drain 行）应作为 0b-4 的必记项，
   尤其 `install_fallback_l0` 需在无 L0 模式下验证为 0。
2. 若后续要压低 3.9×，方向应是 **L2 驻留（阈值/P）**，而不是继续调下沉粒度；
   代价是 →L3 级联上升（B 臂已证）——这是一个需要联合优化的二维问题。
3. 并批策略（`ZF_SINK_BATCH=1`）在 L1 扇出提高到"每分区多个 L1 文件"之前
   不应作为默认；其两个流水修复已随该开关保留，未污染默认路径。
