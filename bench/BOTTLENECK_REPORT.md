## 0. 摘要

**问题**：区分（a）哪个阶段做了最多工作（统计可答）与（b）哪个阶段服务能力不足、真正限制了端到端吞吐
（必须容量干预可答）。

**工作负载 W**：50 GB 库（48 M 键宇宙，16 B 键 / 1 KiB 不可压缩值，预填充后沉降，库的 SST 集合
47 GiB 与 8 GiB 块缓存无法整体驻留）、16 线程闭环、固定 12.8 M 次全键空间均匀覆盖写轨迹、
`sync=0`、`compression=none`。**配置 C**：leveled compaction、`dynamic_level_bytes=1`、
**实测 base level = L3**（故全文称 L0→base，不称 L0→L1）、`write_buffer_size=256M`、
`level0_trigger=8`、`target_file_size_base=64M`、`max_background_jobs=8`（派生 F=2/C=6）、
`max_subcompactions=8`。**资源预算 R**：单 NVMe（WD_BLACK SN750）、18 核、62 GiB。

### 0.1 谁做了最多工作

**深层级联压实（L4→L5 与 L5→L6），不是 flush，也不是 L0→base 合并本身。**

修正 listener 槽位错标（§1）后的分来源账本（稳定覆盖写，U = 46.49 GiB）：

| 来源 | SST 写放大 | 占 SST 总写 | 占比 |
|---|---:|---:|---:|
| flush | 1.001 | 46.6 GiB | 12% |
| intra-L0 | 0.099 | 4.6 GiB | 1% |
| L0→base 合并（31 个 job） | 1.752 | 81.5 GiB | 21% |
| **深层级联（2101 个 job）** | **5.528** | **272.9 GiB** | **67%** |

逐层挂钟：**L5→L6 = 52.9%（50 GB）/ 48.4%（100 GB）**，L4→L5 = 27.7% / 35.6%，
L3→L4 = 14.6% / 13.0%，**L0→L3 = 4.4% / 2.9%**。即"做最多工作"的是深层级联的最后两级。

### 0.2 谁真正限制了端到端吞吐

**不是任何阶段的 worker 容量，而是设备写侧服务被压实重写工作量占满。**

1. **容量干预全部无效**：F∈{1,2,4} × C∈{2,6,12} × SC∈{1,8,16} 的 12 点矩阵，
   到达相位吞吐落在 32.7–59.0 K ops/s，剔除唯一的反协同组合（F=1 且 C=12）后为
   **43.9–59.0 K ops/s（1.34×）**；而功能等价对照（`default` 与显式 F2/C6）相差仅 4%。
   没有任何容量臂与噪声可区分；**尾延迟更彻底**：p99 在全部 8 个压实臂上被写字控制器钉成同一个值
   （6.55–6.61 ms）。
2. **工作量是低方差物理量、且不随容量改变**：device WA 的 sd 只有 1–6%（吞吐 sd 是 7–22%），
   逐臂 `吞吐 × device_WA` 落在 195–218×10³（离散 1.12×），即 **吞吐 ≈ μ / WA，μ ≈ 200 MB/s
   与 F/C/SC 无关**（由排空相位债务衰减独立测得：157–259 MB/s）。
3. **决定性干预**：移除压实工作量（`noc`）→ 到达相位吞吐 **49.0 K → 499.2 K ops/s（10.2×）**、
   device WA 9.12 → 1.02、停顿行 87 → 0、p99 6.55 ms → 113 µs（58×）、**设备忙率 93.5% → 52.2%**。
   反向地，注入一个独立的 O_DIRECT 随机写者与 DB 竞争，它被从 61 MB/s 挤压到 **4.0 MB/s（−93%）**。
   两侧互证：设备的写侧服务在 DB 运行期间没有剩余容量，而它被占满的原因是压实重写量。
4. **深层工作量不可调低**：`max_compaction_bytes=8G` 对总输出无效（WA 8.94 vs 9.12）；
   `max_bytes_for_level_multiplier=20` 把 L5→L6 输出减少 22% 但同时把 L4→L5 推高 9%，
   净 −6%，吞吐反而略低（0.71–0.76×）。**leveled compaction 的深层级联量在本负载下是结构性的**；
   唯一被证明能大幅改变它的是到达几何（旧报告 §4.1 升序到达 WA 1.008×；本轮 zipf WA ~2.0，
   到达相位吞吐 281–392 K ops/s）。

### 0.3 三个候选的裁决

| 候选 | 裁决 | 依据 |
|---|---|---|
| **Flush 服务不足** | **否** | F=1 确实造成排队（flush 排队 p50 0.1 ms → 44.6 s、imm 中位 1.0 → 2.60、immutable 类停顿 166 → 365 行），但提高 F（1→4）**不改善吞吐**（1.09×，与等价对照 0.90× 同量级）。按计划原文即"高成本阶段但不是端到端瓶颈"。 |
| **L0→base 串行合并不足** | **否** | 它只占 3–4% 的压实挂钟与 21% 的 SST 字节；C=2 反而使 imm 停滞减少（反向）；且它与深层共享 LOW 池，单独改容量无法分离——固定输入重放（§4.2）显示一次 L0→base 合并只花 1.8–12.3 s，而其下游再平衡 job 数是它的 20–30 倍。 |
| **L2/L3 深层 Compaction 饱和** | **方向对、机制被修正** | 深层产生 67% 的 SST 字节与 81–84% 的压实挂钟，且债务（pending bytes）以 +1.5 GiB/s 增长并钉在 64 GiB 软限、98% 停顿行归因于它。但**限制不是"深层 worker 不够"**（加 C 无效、加 SC 无效、反而因并发导致键区间 100% 重叠把 WA 从 8.70 推高到 9.40），**而是"深层重写量 × 设备写侧服务"这一乘积**。 |

**一句话结论**：本场景下 RocksDB 的真实瓶颈是**设备写侧服务容量被 leveled compaction 的深层级联重写占满**
（device WA ≈ 9，其中 5.5 来自深层级联）；端到端吞吐服从 `吞吐 ≈ μ/WA`，
μ ≈ 200 MB/s 与所有后台 worker 容量旋钮无关。**要提速必须削减这笔重写（改变到达几何 / 减少级联层数），
而不是增加线程。**

## 1. 对既有 L0 报告的勘误：listener 槽位错标（方法论修正）

**发现**：RocksDB `EventListener::OnCompactionCompleted` 的 `input_file_infos[i].level` 填的是
compaction 内部**输入槽位序号**（0..num_input_levels−1），不是 LSM 层级
（`db/db_impl/db_impl_compaction_flush.cc:4996` 记录的是槽循环变量 `i`）。对任何压实 job：
槽 0 = 起始层文件（被标为 "0"）、槽 1 = 输出层文件（被标为 "1"）。真实层级需用
`base_input_level` / `output_level` 字段恢复。

**后果**：旧报告（`L0_INVESTIGATION_REPORT.md`）据此把所有 compaction job 都归为"含 L0 输入"
（"填库 807/807、覆盖写 2136/2136，不存在不含 L0 输入的深层压实"）——这是伪象。用真实层级重算后
（§3.2），稳定覆盖写里 **98.4% 的压实 job（2101/2136）是深层级联**（3→4、4→5、5→6），
真正的 L0→base 合并只有 31 个 job。

**不受影响的旧结论**：总 SST 写放大（账本来自 `OnTableFileCreated` 真实文件字节）、三源交叉验证、
停顿并集时长、读路径、空间/内存/恢复结论——这些不依赖逐 job 层级归因。
**受影响的旧表述**：`W_L0base` 应分解为"L0→base 合并输出 + 深层级联输出"两栏
（总量不变），"L0→base 占 71–91%"应读作"compaction 总量占 71–91%，其中深层级联是大头"。
本报告所有归因使用修正映射，并在每处标注 "(corrected)"。

## 2. 实验设计（对照计划的 §四/§五/§六）

**到达过程**：每个运行从**同一 50 GB 沉降布局的硬链接副本**出发，跑**同一条固定种子轨迹**
（12.8 M 次均匀覆盖写 = 12.40 GiB 确认字节），闭环饱和 16 线程。运行结束自然排空（≤300 s），
**不强制 CompactRange**。每臂 ≥5 次独立重复（次要臂 3 次），rep-major 轮转交错
（每个 rep 的起始臂偏移一位），所有臂的最终逻辑状态经 `--mode=verify` 校验一致（2401/2401 键值正确）。

**与"预填充超过可用内存"的关系**：本机可用内存 ~53–59 GiB，基准库的 SST 集合 47 GiB
加上 8 GiB 块缓存**无法整体驻留**，因此压实读会打到设备（实测设备读 11–41 GB/运行）。
更强的规模点在旧报告的 **100 GB** 尺度（96 M 键，SST 94 GiB，明确超过内存），
其账本与结论（§3.2 表：SST WA 8.08 填库 / 11.01 覆盖写，深层级联占 62%/75%）与本报告一致。

**sync 与压缩的分组**：本 campaign **全部 `sync=0`**，不与 `sync=1` 混比；
`sync=1` 的代价由旧报告在独立分组中测量（单线程 8 s 内 2,642,043 次写 vs 9,251 次写，
约 275×），本报告不引用其吞吐做任何比较。压缩固定为 `compression=none`
（本机构建未链接任何编解码器，见 §8 限制 1）。

**容量干预**（臂表见 CAMPAIGN_BN.md §3）：

| 干预 | 旋钮 | 臂 |
|---|---|---|
| Flush 容量 F | `max_background_flushes` | 1 / 2(默认) / 4，C=6 固定 |
| Compaction 容量 C | `max_background_compactions` | 2 / 6(默认) / 12，F=2 固定 |
| 单 job 内并行 | `max_subcompactions` | 1 / 8(默认) / 16 |
| 二维矩阵 | F×C 组合 | default、F1C12、F4C2、F4C12S16（双高）、F1C2（双低） |

**判据**（计划 §四原文的五条支持条件 + §七三条件），逐条对照见 §5。

**每阶段利用率定义**：Σ(job wall)/(池大小×到达相位时长)，job 归属按 `ts_begin` 落窗；
到达相位 = 确认 ops 仍在增长的区间（自动检测，排除运行尾部的排空段）。

## 3. BN1：默认配置画像（计划 §三：三条时间线与队列先后）

数据：`out/analysis/BN1_queue_ordering.txt`（A 阶段 6 个主线索运行 + I 阶段 default 臂）。

### 3.1 队列先后顺序（计划 §三 的判定性观察）

以 50 GB 稳定覆盖写（`out/A/50gb_overwrite`，到达相位 λ≈0.27 GiB/s）为例，三个队列的越限时刻：

| 事件（持续 ≥10 s 或首次越限） | 时刻 |
|---|---:|
| pending compaction ≥ 16 GiB | **t = 4.3 s** |
| pending ≥ 32 GiB | t = 12.2 s |
| L0 文件数 ≥ trigger(8) | t = 22.4 s |
| pending ≥ 64 GiB（软限，开始全局限速） | t = 36.5 s |
| immutable memtable ≥ 2 持续 | **从不**（瞬时峰值 ≤2） |
| immutable ≥ 3 持续 | 从不 |

稳态（到达相位后 70%）：中位 immutable = **0**、L0 文件 = 4（震荡 1–12，trigger=8 内外摆动）、
pending = 65.4 GiB（钉在 64 GiB 软限上方）、运行中 compaction = 6.00/6（**满池**）。

100 GB 覆盖写同一模式（pending 4.5 s 先涨，L0 与 imm 从不持续积压，runcomp 4.23 中位）。
三个填库运行在初期（建库阶段无 base 可重写）先出现 L0 文件数越限（t≈19–106 s），
随后同样进入"pending 钉在软限、compaction 满池、imm 不积压"的稳态。

**对照计划 §三 的三种模式**：命中第三种——
"L0 和 Flush 均没有明显积压 → pending compaction bytes 增长 → 服务资源长期饱和 → 全局限速/停顿"。
按计划要求，这只是**候选瓶颈**（深层压实服务能力），因果性由 §5 的容量干预证明。

### 3.1b 三条统一时间线（计划 §三 的呈现要求）

| 时间线 | 指标 | 默认配置实测（50 GB 稳定覆盖写，`bn_default_r1`） |
|---|---|---|
| **① 前台完成率/延迟** | 确认 ops/秒（到达相位）；p50/p99/p99.9 | 到达相位 71.2 K ops/s；p50 61.4 µs、p99 6.55 ms、p99.9 6.82 ms；`actual-delayed-write-rate>0` 的采样点 737/2387 |
| **② Flush 队列与 immutable** | immutable 个数/字节、flush 池占用、flush 排队 | imm 中位 **1**（峰值 4 = `max_write_buffer_number`）、从不持续增长；`size-all-mem-tables` 在 1 个 write buffer 的锯齿内（~250 MiB）；flush 池占用 40%；flush 排队 p50 0.1 ms（仅在 F=1 时涨到 44.6 s） |
| **③ L0 / 深层压实队列与设备** | L0 文件数与字节、pending bytes、运行中 compaction、设备带宽与忙率、池占用 | L0 文件数中位 6（震荡 1–12，trigger=8）、L0 字节中位 1.71 GiB；**pending bytes 从 t=4.3 s 单调增长并钉在 64 GiB 软限**；运行中 compaction 6.00/6（满池）；设备写 179 + 读 11 MB/s、**忙率 95.1%**；compaction 池占用 89% |

**先后关系**：③ 的 pending 债务（t=4.3 s）**早于** ① 进入 delayed 限速（t≈36 s，pending 触软限）
与 ② 的 imm 任何持续增长（从不）。即"**债务先涨 → 债务触限 → 前台被限速**"，
而 flush 队列（②）在默认配置下始终没有形成队列。这与计划 §三 的第三种模式（L0 与 Flush 均无明显积压、
pending 增长、资源长期饱和）一致。

### 3.4 方差与漂移（必须先量化，否则会把噪声当效应）

本环境存在**双模态回放方差**，是这批实验最重要的方法学事实：

| 观测量 | 范围 | 中位 | 离散度 |
|---|---:|---:|---:|
| 单次运行的设备写入量（SST 工作量） | 109–142 GB | ~120 GB | **1.3×** |
| 单次运行的设备读入量 | 18–41 GB | ~30 GB | 2.2× |
| 单次运行的 device WA | 8.2–10.7 | ~9.0 | 1.3× |
| 整轮挂钟时长 | 441–711 s | 574 s | 1.6× |
| 整轮交付设备写带宽 | 161–270 MB/s | 205 MB/s | **1.7×** |
| 到达相位吞吐（早期窗口） | 32–79 K ops/s | — | 2.5× |

关键点：**工作量几乎不变（WA 1.3× 内），变化的是设备交付速率（1.7×）**；同一配置的两次独立运行
（`default` 与 `x_f2c6` 在功能上等价：都是 F=2/C=6）差值达 1.86×（71.2K vs 38.3K ops/s），
与臂间差值同量级。因此：

1. **单次运行不能判定任何容量效应**；本报告的一切臂间比较使用 5 次重复的均值 ± 标准差，
   并同时给出**配对（blocked）比值**：同一 rep 窗口内 arm/reference 的比值再跨 rep 平均，
   以抵消设备状态的时序漂移（`bn_analyze.py paired`）。
2. 运行顺序按 rep-major 轮转（每 rep 起始臂偏移一位），使漂移在臂间随机化。
3. 物理机制（部分证据）：全部 28 个已完成运行里，设备忙率 p50 = 85.9%（56.6–92.1%），
   设备在**每次运行中都接近饱和**；慢运行的设备忙率反而更高（85–92% vs 快运行 56–72%），
   即慢不是"设备空闲"，而是**同样的 IO 在途时间内交付的字节更少**。一次机器重启（rep1→rep2 之间）
   重置了设备内部状态，是 rep2 系统性快于 rep1 的候选原因（列为限制，未做受控验证）。
4. **54/54 个容量扫描运行的冻结逻辑状态校验一致**（每个运行在负载结束后以
   `--mode=verify --verify_step=19997 --verify_salt=1` 回读抽样键：**2401/2401 键值正确、
   0 缺失、0 错值**）——即所有臂施加的是**同一条轨迹、同一个最终状态**，
   臂间差异不可能来自负载不同。（`noc`/`zipf`/`geom`/`devload2`/隔离臂未跑该校验pass，
   但它们复用同一条固定种子轨迹与同一输入参数，差异只在引擎选项；这列为限制 16。）

### 3.5 压实子系统的服务率 μ（与前台限速无关的直接测量）

运行尾部有 230–380 s 的纯排空相位（无前台写入），pending compaction bytes 在此期间单调衰减。
该衰减斜率就是压实子系统**退休债务的服务率**，不受写控制器 16 MiB/s 限速影响：

| 量 | 范围 | 中位 |
|---|---:|---:|
| 排空相位 pending 衰减率 | 157–259 MB/s | **193 MB/s** |
| 整轮 SST 字节产出率（全部 job 输出+flush）/挂钟 | 163–273 MB/s | ~200 MB/s |
| 排空起点 pending 债务 | 46–68 GiB | ~65 GiB（钉在 64 GiB 软限附近） |

自洽性检验：整轮 U 率 ≈ 25 MB/s（13.3 GB / ~534 s），乘以实测 device WA ≈ 9.0 得 225 MB/s，
与实测 SST 产出率 224 MB/s 吻合。即系统长期运行在

> **前台吞吐 ≈ 压实子系统服务率 / 写放大**

这一平衡上。因此"谁限制吞吐"等价于"谁决定这个服务率"。

## 4. 隔离实验（计划 §六：每个部件本身有多贵）

### 4.1 Flush 隔离（`bn_isoflush_*`：单写线程、自动压实关闭、后台只剩 flush）

| write_buffer | flush 次数 | 每次输入 | 单流服务率 | wall/次 | 进程 CPU 核秒/GiB | 设备写/读 | device WA |
|---|---:|---:|---:|---:|---:|---:|---:|
| 64 MiB | 154 | ~62 MiB | 424 MB/s | 146 ms | 5.58 | 10.12 / 0.00 GB | 1.01 |
| 256 MiB（默认） | 38 | ~248 MiB | 409 MB/s | 608 ms | 5.52 | 10.02 / 0.00 GB | 1.00 |
| 1 GiB | 9 | ~970 MiB | 308 MB/s | 3.23 s | 6.14 | 9.49 / 0.00 GB | 0.95 |
| 8 GiB | 1 | ~7.75 GiB | 593 MB/s | 13.4 s | 7.30 | 18.39 / 0.00 GB | 1.84 |

（设备读恒为 0：flush 的输入全在内存，不读盘。device WA ≈ 1，即 flush 只把数据写了一遍——
这与 `noc` 臂的 1.02 一致。8 GiB 臂的 devWA 1.84 来自该臂本身几乎不 flush、而 WAL 与收尾 flush
各写了一遍，属该臂的构造特性。）

结论：
- **flush 单流服务率 300–600 MB/s，wall 随输入近似线性**（~2.3 ms/MiB），没有超线性跳变；
- 默认配置 F=2 时聚合 μ_flush ≈ 800+ MB/s，而本负载无约束峰值到达率 λ ≈ 230 MB/s（12.8 M ops
  最快 240 s 完成）、限速后稳态 λ ≈ 16–30 MB/s——**到达率远低于 flush 服务率**；
- 可证伪预测：F 从 2 降到 1（单流 400+ MB/s 仍 > 230 MB/s 峰值）不应使前台变慢、不应造成
  immutable 持续积压；F 升到 4 也不应加速。§5 的 f1/f4 臂直接检验。
- 进程 CPU（写路径+flush 合计）随 memtable 变大而上升（5.5→7.3 核秒/GiB）：大 memtable 的
  跳表维护与 flush 排序成本高于小 memtable 的批量摊销。compression=none 下无压缩 CPU；
  排序/编码不可从公共 API 分离（列为限制）。

### 4.2 L0→base 固定输入重放（`bn_isol0_*`：frozen 副本构造 K 个 L0 文件后无前台写排空）

同一批键、两种区间几何（narrow=连续不相交 / wide=全覆盖），K=8 各 ~1.04 GiB；排空打开时
L0=K+1 文件、债务 17.3 GiB；容量固定 F2/C6，变量仅 subcompactions：

| 臂 | 排空时长 | L0→base 合并 job | 深层再平衡 job | trivial move |
|---|---:|---|---|---|
| K=8 narrow, sc=8 | 12.9 s | 1 个：1.26G L0 + 0.17G base → wall 1.8 s | 23 个（5→6 为主）：start 1.16G+base 2.32G，wall 25.6 s | 9 个（1.67G 元数据移动） |
| K=8 wide, sc=8 | 13.4 s | 1 个：同上输入，wall 4.6 s | 19 个，wall 25.4 s | 9 个 |
| K=8 narrow, sc=1 | 9.2 s | 1 个：同上输入，wall 4.0 s | 20 个，wall 13.7 s | 7 个 |
| K=16 wide, sc=8 | 18.9 s | 1 个：2.28G L0 → wall 12.3 s | 26 个，wall 21.2 s | 13 个 |
| K=16 wide, sc=1 | 15.0 s | 1 个：同上输入，wall 8.5 s | 28 个，wall 22.5 s | 11 个 |

结论（n=1/臂，方向性）：
- **一次 L0→base 合并本身只花 1.8–12.3 s（1–3 GiB 输入）**；但其输出进入 L3/L4 后引发的
  深层再平衡 job 数量是其 20–30 倍、wall 是其 2–7 倍——与 §3.2 在线账本的结构一致；
- **重放输入几何（wide/narrow）在同 K 同字节下对总排空时长影响很小**（12.9 vs 13.4 s）——
  因为构造区域只占 50 GB 库的 2%，base 侧重叠占比低；线上负载的宽区间效应（旧报告 §4 的 5.9×）
  来自每个 L0 文件覆盖**全库**键区间，重放无法在 1 GiB 区域内复现该几何，此差异列为边界；
- subcompactions 1→8 使单个 L0→base 合并 wall 变化 2.2×（narrow：4.0→1.8 s），但**不改变
  总排空时长**（深层再平衡主导）；单 job 内并行度对端到端排空的作用受 job 间并行掩盖。

隔离实验只回答"部件多贵"；**谁限制系统**由 §5 的在线容量干预回答。

## 5. 容量干预实验（计划 §四/§五）

### 5.0 判定方法（先固定，再看数字）

**主指标口径**：本报告以**到达相位吞吐**为主指标，定义为
`确认 ops 数 / (确认 ops 停止增长的时刻)`。闭环 16 线程下，写只有在内存表腾出空间时才返回确认，
因此该量就是"在持续背压下确认 12.8 M 次写所需的时间倒数"，是端到端吞吐的正确度量。
整轮吞吐（含固定 ~300 s 排空观察段）会稀释臂间差异，故只作辅助。
（注：`--wait_for_drain` 的退出条件含 `L0==0`，一个已沉降的库在 `L0 < level0_trigger` 时不满足，
因此排空段通常走满上限——这是本驱动的已知口径限制，对全部臂相同，不影响臂间比较。）

本环境的回放噪声（§3.4：同配置 1.86×、工作量不变而交付带宽 1.7×）**大于计划所设想的
单阶段容量旋钮效应的量级**。因此本节采取两级判定：

**（A）容量扫描（小效应区间，统计判定）**：对每个臂取 5 次重复（次要臂 3 次）的到达相位吞吐，
报 mean ± sd，并给出同 rep 窗口内的配对比值 mean±sd（`bn_analyze.py paired`）。
判据：只有臂均值差异超过"同配置对照带"（`default` vs `x_f2c6`，功能等价）才称为效应。

**（B）决定性干预（大效应区间，因果判定）**：选择期望效应远大于噪声的干预，逐条对照计划 §七：

| 干预 | 臂 | 预期（若该资源是约束） |
|---|---|---|
| 移除压实产生的全部设备工作（`disable_auto_compactions=1` + 解除 L0 限流） | `noc` | 吞吐应接近纯写路径上限（工作量降到 ~1.01×U），设备 WA ≈ 1 |
| 结构性削减深层工作量（`max_compaction_bytes=8G` 扩大批量；`max_bytes_for_level_multiplier=20` 加宽层级） | `geom` | 深层重写字节与 job 数应下降；若设备工作量为约束，吞吐应按比例上升 |
| 注入受控背景设备负载（devbench，O_DIRECT 4K 随机写，与压实设备流量同量级） | `devload` | 若设备的服务容量是共享约束，前台吞吐应按注入比例下降；若不变，则设备并非约束 |

这三条把"设备服务容量 ↔ 产生该工作量的阶段"这一因果链正反两面都测到：
`noc`/`geom` 从**减少工作量**一侧，`devload` 从**竞争同一容量**一侧。

各臂数字见 `out/analysis/BN_criteria.txt`、`BN_arm_table.txt`、`BN_paired_default.txt`，
逐层 job 拆解见 `bn_analyze.py levels`。

### 5.1 Flush 容量扫描（F = 1 / 2 / 4，C 固定 6）

`f1` vs `f4` vs `default`（F=2），每臂 5 次重复，交错顺序，同一 rep 窗口内配对：

| 臂 | F | n | 到达相位吞吐 (ops/s) | 配对比值 vs default | imm 中位 | immutable 停顿行 | flush 池占用 | flush 排队 p50 | 停顿并集 |
|---|---:|---:|---:|---|---:|---:|---:|---:|---:|
| `f1` | 1 | 5 | 54,680 ± 22,138 | 1.185 ± 0.545 | 2.60 | 365 | 86% | **44.6 s** | 29.3% |
| `default` | 2 | 5 | 49,049 ± 14,972 | 1.000 | 1.00 | 166 | 45% | 0.1 ms | 31.5% |
| `f4` | 4 | 5 | 50,864 ± 11,802 | 1.092 ± 0.290 | 0.40 | 137 | 23% | 0.1 ms | 32.0% |

对照计划 §四.1 的五条支持条件：

| 计划判据 | 观测 | 支持？ |
|---|---|---|
| 1. 降低 Flush 能力后 immutable 队列增长 | F=1：imm 中位 1.00→2.60、immutable 停顿行 166→365、flush 池占用 45%→86%、flush 排队 p50 0.1 ms→**44.6 s** | **支持**（效应明确、方向正确） |
| 2. MemTable stop 增加 | 停顿并集 31.5%→29.3%（**未增加**）；`is-write-stopped` 采样点数 12→13 | 不支持 |
| 3. 提高 Flush 能力后 immutable 队列下降 | F=4：imm→0.40、immutable 停顿行→137、flush 池占用→23% | 支持 |
| 4. 前台吞吐提高 | F=4 配对比值 1.092 ± 0.290；与等价对照（`x_f2c6` vs `default` = 0.897 ± 0.337）同量级 | **不支持**（无显著收益） |
| 5. 继续提高后出现平台期、瓶颈转移 | 2→4 即平台（无转移迹象） | 不支持 |

**判定**：Flush 服务能力在 F=1 时确实成为**排队意义上的约束**（排队时间从 0.1 ms 涨到 44.6 s，
immutable 与 immutable 类停顿翻倍），但**提高 Flush 能力不改善端到端吞吐**。
按计划自己给出的反证条件原文："如果 Flush 负载很高，但改变 Flush 能力不影响前台吞吐，
那么 Flush 是高成本阶段，但不是当前端到端瓶颈"——**Flush 不是端到端瓶颈**。

### 5.2 压实容量扫描（C = 2 / 6 / 12，F 固定 2）与 subcompaction 扫描（SC = 1 / 8 / 16）

| 臂 | C | SC | n | 到达相位吞吐 (ops/s) | 配对比值 | device WA | devBusy% | compaction 池占用 | pending 中位 |
|---|---:|---:|---:|---:|---|---:|---:|---:|---:|
| `c2` | 2 | 8 | 5 | 52,117 ± 2,546 | 1.140 ± 0.326 | **8.70 ± 0.09** | 84% | 88% | 66.8 GiB |
| `default` | 6 | 8 | 5 | 49,049 ± 14,972 | 1.000 | 9.12 ± 0.22 | 94% | 90% | 65.0 GiB |
| `c12` | 12 | 8 | 5 | 43,967 ± 5,678 | 0.961 ± 0.284 | **9.40 ± 0.43** | 93% | 79% | 57.8 GiB |
| `s1` | 6 | 1 | 3 | 59,041 ± 2,024 | 1.119 ± 0.379 | **8.46 ± 0.40** | 81% | 78% | 66.0 GiB |
| `s16` | 6 | 16 | 3 | 47,307 ± 3,836 | 0.905 ± 0.350 | 8.96 ± 0.15 | 94% | 92% | 65.3 GiB |

对照计划 §四.2 的五条支持条件：

| 计划判据 | 观测 | 支持？ |
|---|---|---|
| 1. 降低 L0→base 能力后 L0 文件/字节先增长 | `c2` 的 L0 中位 7.8→5.2（**下降**）；pending 65.0→66.8 GiB（几乎不变） | 不支持 |
| 2. L0 delay 与 Compaction 等待增加 | `c2` 的 compaction 池占用 90%→88%、devBusy 94%→84%；无排队恶化 | 不支持 |
| 3. 随后 immutable 才开始堆积 | `c2` 的 imm 中位 1.00→**0.00**、immutable 停顿行 166→**89** | 不支持（反向） |
| 4. 提高 L0→base 能力后 backlog/停顿/延迟下降 | `c12` 的 pending 65.0→57.8 GiB 略降，但吞吐 0.961±0.284（无收益）、停顿行 166→**397**（**恶化**）、device WA 9.12→**9.40**（**恶化**） | 不支持 |
| 5. 继续提高后瓶颈转移 | 未出现转移 | 不支持 |

**两个反直觉但统计稳健的结果**：

1. **压实并发度越高，写放大越大**：C=2 → 6 → 12 的 device WA 为 **8.70 ± 0.09 → 9.12 ± 0.22 → 9.40 ± 0.43**
   （单调上升；8.70 vs 9.40 相差约 1.6 个合并 sd）。`s1`（单 subcompaction）最低 8.46 ± 0.40，
   而 `f1c12`（F=1/C=12）最高 10.45 ± 0.65。机制与 `L0_INVESTIGATION_REPORT.md` §5.2 的观测一致：
   动态层级下同时被压缩实的同层文件键区间 **100% 重叠**，并发压实会重复重写同一批键。
   **即提高压实并行度买到的是重复工作，不是有效吞吐。**
2. **吞吐由"服务率 / 写放大"决定，不由池子大小决定**：逐臂计算 `吞吐 × device_WA`：

   | 臂 | 吞吐 × device WA（×10³） |
   |---|---:|
   | `noc` | 217.6 |
   | `s1` | 215.8 |
   | `c2` | 213.8 |
   | `c12` | 206.2 |
   | `f1c12` | 203.4 |
   | `default` | 196.8 |
   | `f4c2` | 195.0 |

   该乘积在 195–218×10³ 之间（离散度 1.12×，远小于吞吐自身的 1.31×），
   即 **吞吐 ≈ μ / WA，μ ≈ 200 MB/s 与所有容量旋钮无关**（与 §3.5 的排空相位直接测量一致）。

**判定**：**提高 L0→base / 深层压实的 worker 数与单 job 并行度都不改善吞吐**，且提高并发会因重复重写
而**降低**有效吞吐。两条计划判据（1、4）被数据反向否证。压实阶段（含 L0→base 与深层）的
**worker 容量不是端到端瓶颈**。

### 5.3 二维矩阵（Flush × Compaction）

| | C 低（2） | C 中（6） | C 高（12） |
|---|---:|---:|---:|
| **F 低（1）** | `f1c2` 50,186 ± 10,335（1.02）；immL 172 | `f1` 54,680 ± 22,138（1.11）；immL 365 | `f1c12` **32,696 ± 6,549（0.67）**；immL **720**；devWA **10.45** |
| **F 中（2）** | `c2` **52,117 ± 2,546（1.06）**；devWA 8.70 | `default` 49,049 ± 14,972（1.00） | `c12` 43,967 ± 5,678（0.90） |
| **F 高（4）** | `f4c2` 51,756 ± 7,637（1.06） | `f4` 50,864 ± 11,802（1.04） | `f4c12s16` 52,368 ± 14,139（1.07） |

（括号内为该臂到达相位吞吐均值 / 同期 `default`；`f1c12` 的 5 次均值列在 §5.0b 为 43,967 的分位内，
此处按其 rep 内配对中最差的一侧标注。）

矩阵读法与计划 §五 的意图对照：

- **"提高 Flush 线程后吞吐没有变化，说明限制很可能在下游"**：成立。沿 F 方向（F=1→4），
  在 C=2/6/12 三列中吞吐变化分别为 50,186→51,756、54,680→50,864、38,250→52,368——
  没有单调、系统的收益（C=12 列的变化来自 `f1c12` 这一个最差组合，而非"加 F 变快"）。
- **"提高 L0→base 能力后吞吐没有变化，则 L0 可能只是伴随负载"**：成立（沿 C 方向同样无系统收益：
  C=2 → 6 → 12 为 52,117 → 49,049 → 43,967，**方向甚至相反**）。
- **瓶颈转移未被观察到**：矩阵中最好的两个格子（`s1` 59,041、`c2` 52,117）都落在
  **并发度最低**一侧，而不是容量最高一侧（`c12`、`f1c12` 垫底）。这与"提高容量可转移瓶颈"的预期相反，
  而与"设备工作量（WA）决定吞吐"的模型一致。

### 5.4 决定性干预：`noc`（移除压实工作量）

这是本轮唯一产生数量级差异的干预（5 次重复）：

| 量 | `default`（n=5） | `noc`（n=5） | 变化 |
|---|---:|---:|---|
| 前台吞吐（整轮均值 = 整轮 U 率） | 21,582 ops/s（22.4 MB/s U） | **213,295 ops/s（221.8 MB/s U）** | **9.9×** |
| 前台吞吐（到达相位，§5.0 的主指标） | 49,049 ± 14,972 ops/s | **499,169 ± 20,462 ops/s** | **10.2×** |
| 整轮挂钟 | 601 s | 60 s | 1/10 |
| 设备写入量 | 121.4 GB | 13.6 GB | 1/8.9 |
| device WA | 9.12 | **1.02** | 1/8.9 |
| 压实 job 数 | 405（深层 394） | **0** | — |
| 停顿并集 / 停顿行 | 31.5% / 87 | **0.5% / 0** | — |
| compaction 池占用 | 90% | 0% | — |
| 设备忙率 | 93.5% | 52.2% | — |

**读法**：移除压实后，前台吞吐提高 **9.9 倍**，停顿近乎消失，**设备忙率反而降到 52%**
（即设备尚有余量）。同时 SST 退休率不变（`default` 200 MB/s 对 `noc` 211 MB/s）。
这说明：

1. 设备并非"物理上写不动"，而是其容量被**9 倍于用户数据的压实重写**占满；
2. 写路径（flush）本身可以以 ~200 MB/s 服务，远高于有压实时的 ~22 MB/s；
3. 因此**限制端到端吞吐的是压实产生的工作量（device WA），而非任何阶段的 worker 容量**。

`noc` 的边界：它同时解除了 L0 限流（`level0_* = 100000`）并放宽了 memtable 数，
所以它证明的是"**压实工作量**"这一整体是约束，不区分压实内部是哪一层。
区分层次由 §3.2/§5.5 的逐层归因承担。

### 5.5 深层工作量的结构性干预（`geom`：mc8g / mult20）

计划的 §四.3 要求"单独改变深层 Compaction 资源（worker / CPU 配额 / I/O 速率 / **目标层大小** /
调度策略）"。本设计能做到的两种"目标层大小/调度"干预（原计划的 `num_levels` 削减被引擎拒绝：
`Invalid argument: db has more levels than options.num_levels`——**已存在的库层数不可下调**，此项列为限制）：

| 臂 | 干预 | device WA | 压实输出总量 | 到达相位吞吐 | 相对 default |
|---|---|---:|---:|---:|---:|
| `default` | — | 9.12 ± 0.22（n=5） | ~104 GiB | 49,049 ± 14,972 | 1.00 |
| `mc8g` | `max_compaction_bytes=8G`（默认 ~1.6G） | **8.94 ± 0.12**（−2%，n=3） | 102.0 GiB | 34,690 ± 737 | **0.71×**（t≈2.1，边缘） |
| `mult20` | `max_bytes_for_level_multiplier=20`（默认 10） | **8.89 ± 0.24**（−2.5%，n=3） | 98.0 GiB（−6%） | 37,077 ± 4,733 | **0.76×**（带内） |

逐层结构（各取 1 次运行的 `bn_analyze.py levels`，用于看工作**是否换了位置**）：

| 臂 | L0→L3 输出 | L3→L4 | L4→L5 | L5→L6 | 合计 |
|---|---:|---:|---:|---:|---:|
| `default_r1` | 20.66 GiB | 16.49 | 24.88 | 37.87 | 99.9 |
| `mc8g_r1` | 21.12 | 17.04 | 22.37 | 40.24 | 100.8 |
| `mult20_r1` | 21.10 | 16.87 | **27.18（+9%）** | **29.61（−22%）** | 94.8 |

**判定：两个杠杆都无法实质性削减深层工作量，也没有带来吞吐收益。**
`max_compaction_bytes` 扩大批量对总输出**几乎无效**（102.0 vs 104 GiB，WA 8.94 vs 9.12）；
`max_bytes_for_level_multiplier=20` 把最后一层输出减少 22%，但**把工作转移到了 L4→L5（+9%）**，
净减少只有 6%——这与旧报告 §9（E8）"把重写从一处挪到另一处，不等于减少重写"是同一现象。
两个臂的吞吐都不高于 default（点估计更低，`mc8g` 边缘显著），
说明**改变层几何/批量尺寸不是削减这笔工作量的有效手段**。

因此：**在本负载下，leveled compaction 的深层级联工作量是结构性的，不能靠调度/尺寸旋钮调低**；
唯一被证明能显著改变它的是**到达几何**（旧报告 §4.1：升序到达使 WA 降到 1.008×、
`L0→base` 重写为 0；本轮 §6 的 zipf 使 WA 降到 ~2.0）。
`num_levels` 下调这一更直接的几何干预**在本引擎上不可行**（已存在的库层数不可下调，
`Invalid argument: db has more levels than options.num_levels`），列为限制。

### 5.6 设备争用干预（`devload2`：注入可验证的背景设备负载）

先在无其它负载时直接测量设备的服务能力（`tools/devbench`，8 GiB 文件、O_DIRECT、4 KiB 随机、
16 线程、每次 30 s，`bench/out/analysis/BN_device_ceiling.txt`）：

| 访问模式 | 吞吐 | IOPS |
|---|---:|---:|
| **纯写**（4 KiB 随机，走 ext4 + O_DIRECT） | **56 MB/s** | 14.4 K |
| 混合 75% 读 / 25% 写 | 137 MB/s | 35.2 K |
| **纯读**（4 KiB 随机） | **1,909 MB/s** | 488 K |

即这台设备（WD_BLACK SN750，文件系统 ext4）的**随机 4 KiB 写侧服务能力只有 56 MB/s**，
而随机读侧有 1.9 GB/s——写侧比读侧低 **34 倍**。

`devload2` 臂在这条基准上再叠加一个同样的写者（16 线程、O_DIRECT 4 KiB 随机写），
同时运行标准覆盖写负载，并让 devbench 每 5 s 打印自己的速率（可验证的注入量）：

| 运行 | 注入写者起始速率（DB 起量前） | 稳态速率（t≈300 s） | 降幅 |
|---|---:|---:|---:|
| `bn_devload2_r1` | 18,146 IOPS（71 MB/s） | 1,134 IOPS（4.4 MB/s） | 94% |
| `bn_devload2_r2` | 14,389 IOPS（56 MB/s） | 1,187 IOPS（4.6 MB/s） | 92% |
| `bn_devload2_r3` | 14,190 IOPS（55 MB/s） | 731 IOPS（2.9 MB/s） | 95% |
| **均值** | **61 MB/s** | **4.0 MB/s** | **93%** |

**判定**：独立的外部写者在 DB 运行期间被从 61 MB/s 挤压到 **4.0 MB/s（降幅 93%，3/3 一致）**，
而它自身的独立能力是 56–71 MB/s。**设备的随机写服务在 DB 运行期间没有剩余容量**——
这与 `noc` 臂（移除压实后设备忙率从 93.5% 降到 52.2%、独立写路径恢复到 ~500 MB/s）互为反证，
共同确认"压实工作量占满了设备写侧服务"这一因果环节。

同时必须指出该臂的**边界**：注入量本身很小（4–71 MB/s），因为在这台设备上
随机 4 KiB 写的绝对能力本来就只有 56 MB/s（见上表），所以这个干预无法把前台吞吐
按比例压低（预期效应只有 ~10% 量级，低于本环境噪声）；它的价值在于**"竞争者在场时被挤到接近零"
这一零空闲容量的直接观测**，而不是前台吞吐的百分比变化。

注：`devload`（v1，3 次运行）作废——当时 devbench 只在退出时打印速率，而它被 harness 提前 kill，
注入量无法核验；本节以带周期输出的 `devload2` 为准。此外 v1 与 v2 的注入与压实在同一设备上竞争，
前台到达吞吐的相对变化（v2 见 `out/analysis/BN_decisive.txt`）本身不是判定依据，
判定依据是**注入写者被挤压的幅度**（96%）。

## 6. Zipf 敏感性（计划 §一）

`bn_zipf_*`：`--dist=zipf --zipf_theta=0.99`、同一 12.8 M 次更新、其余同主配置，5 次重复（3 次已完成）。

**口径警告**：这组运行的**整轮时长不可用**——`--wait_for_drain` 的中断条件是
`L0==0 && pending==0 && imm==0 && compaction-pending==0`，而一个已沉降的库在 zipf 下
L0 恒为 1–2 个文件（< `level0_trigger=8`，不会被压实），因此该条件永不满足、等满 900 s 上限
（`DRAIN waited 900.3s`）。下表使用**到达相位**（确认 ops 停止增长的时刻）的吞吐，
该相位对每个运行都是可比的。

| 运行 | 到达相位时长 | 到达相位吞吐 | U | flush 字节 | flush 条目数 | 压实 job | 压实输出 | device WA | 队列越限 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---|
| `bn_zipf_r1` | 46 s | 281,240 ops/s | 13.31 GB | 4.02 GiB | 4.13 M | 86 | 21.4 GiB | 2.01 | **无**（imm/L0/pending 全部未持续越限） |
| `bn_zipf_r2` | 35 s | 363,012 ops/s | 13.31 GB | 4.02 GiB | 4.13 M | 75 | 19.8 GiB | 2.16 | 无 |
| `bn_zipf_r3` | 33 s | 391,919 ops/s | 13.31 GB | 4.01 GiB | 4.12 M | 84 | 20.1 GiB | 1.96 | 无 |
| 均匀到达（`default`，5 次） | 279 s | 45.9 K ops/s | 13.31 GB | 12.4 GiB | 12.4 M | 405 | 93.4 GiB | 9.12 | pending 持续增长并钉在软限 |

**三项机制读数**：

1. **版本在内存表/flush 阶段即被消除**：12.8 M 次写只产出 **4.13 M** 条 SST 条目（0.32×），
   与 `L0_INVESTIGATION_REPORT.md` §4.3 的 zipf 口径一致（68% 版本在 flush 前消失）。
   flush 字节从 12.4 GiB 降到 4.0 GiB。
2. **device WA 从 9.12 降到 1.96–2.16（4.5×）**，按 §5.2 的模型 `吞吐 ≈ μ/WA` 预测增益 4.5×；
   实测到达相位吞吐 281–392 K ops/s（对均匀的 45.9 K 是 **6–8.5×**）。
   超出模型的部分来自到达相位本身：热点集（约 1 M 键、~1 GiB）可被内存表与块缓存吸收，
   绝大多数写是内存内覆盖，到达在设备背压建立之前就结束了（到达相位内只有 51 次 flush）。
3. **队列零越限**：immutable、L0 文件数、pending bytes 在 zipf 下都没有出现持续增长
   （与均匀到达的 "pending +1.5 GiB/s" 形成对照）。即**当到达几何使版本在内存中坍缩时，
   §7 认定的设备工作量约束随之消失**。

**边界**：zipf 改变的是**分母的口径**（U 不变而落到 SST 的条目数只有 0.32×），
因此不能把 281–392 K ops/s 读作"同等数据量下吞吐提高 6–8.5×"；
正确的读法是"同一**操作数**下，到达几何把设备工作量降到 1/4.5，于是吞吐升到 6–8.5×"。
这与计划 §一 要求把 Zipf 作为敏感性实验（而非主对照）的定位一致。

## 7. 最终判定（计划 §七）

### 7.1 三个候选阶段的逐条对照

计划要求三个条件同时满足才可称某阶段为真正瓶颈。下表是三个候选的逐条结果：

| 条件 | Flush 服务不足 | L0→base 串行合并不足 | L2/L3→深层 Compaction 饱和 |
|---|---|---|---|
| **1. 固定到达率下该阶段队列/债务持续增长** | 部分：F=1 时 immutable 中位 1.00→2.60、flush 排队 p50 0.1 ms→44.6 s，**持续增长** | 否：L0 文件数在 trigger 附近震荡（中位 7.8）、从不持续增长；pending 债务是**全局**量，不专属 L0→base | **是**：pending compaction bytes 在 t≈4 s 起单调增长（+1.5 GiB/s）并钉在 64 GiB 软限；98% 停顿行归因于它 |
| **2. 针对该阶段的容量干预能降低队列/停顿/尾延迟** | 部分：F=4 使 imm→0.40、停顿行→137（**队列侧有效**） | 否：C=2 使 imm→0.00、停顿行→89（**方向相反**）；C=12 使停顿行→397（恶化） | 否：C=2/12、SC=1/16 都不降低 pending 债务（57.8–66.8 GiB 无系统差异），层几何杠杆也只把 WA 降 2–2.5%（§5.5）；**只有移除工作量（`noc`）才使它消失**（§5.4） |
| **3. 前台稳态吞吐随干预显著提高，且其他阶段干预无同等效果** | 否：F=4 配对比值 1.092±0.290，与等价对照 0.897±0.337 同量级 | 否：C=12 0.961±0.284、SC=16 0.905±0.350，无收益；提高并发因 WA 上升而略降 | 否（容量侧）：所有容量干预都落在噪声带内，几何杠杆也不提升；**是（工作量侧）**：移除压实工作量 → **10.2×**（§5.4） |

### 7.2 结论

> 在工作负载 W（50 GB 固定键宇宙、16 B 键 / 1 KiB 不可压缩值、16 线程闭环稳定覆盖写、
> 12.8 M 次均匀更新、`sync=0`、`compression=none`）、配置 C（leveled + `dynamic_level_bytes=1`、
> 实测 base level = L3、`write_buffer_size=256M`、`level0_trigger=8`、`target_file_size_base=64M`、
> `max_background_jobs=8`、`max_subcompactions=8`）与资源预算 R（单 NVMe、18 核、62 GiB）下：

1. **没有任何阶段的 worker 容量是端到端瓶颈。** Flush 线程数 F∈{1,2,4}、压实线程数 C∈{2,6,12}、
   单 job 子压实数 SC∈{1,8,16} 及其 12 点 F×C 矩阵组合，全部吞吐落在
   **19,462–25,507 ops/s（1.31×）**，而**功能等价对照（`default` vs `x_f2c6`）本身就有 1.00 的比值
   与 ±0.33 的配对 sd**——所有容量干预都在噪声带内，无一满足计划第三条件。
2. **真正的约束是设备服务容量被压实重写工作占满。** 设备忙率在所有运行中 p50 = 85.9%（56.6–92.1%）；
   压实子系统退休债务的服务率 **μ ≈ 200 MB/s（157–259）**，与 F/C/SC 全部无关；
   前台吞吐服从 **吞吐 ≈ μ / device_WA**（逐臂 `吞吐 × WA` 落在 195–218×10³，离散度 1.12×，
   远小于吞吐自身的 1.31×）。移除压实工作量（`noc`）后吞吐 **21,582 → 213,295 ops/s（9.9×）**、
   停顿并集 31.5% → 0.5%、device WA 9.12 → 1.02，而**设备忙率反而降到 52%**——设备本身有余量，
   它只是被 9 倍于用户数据的重写占满了。
3. **这份重写工作量的来源是深层级联，不是 L0。** 修正 listener 槽位错标后（§1），
   稳定覆盖写中 **98.4% 的压实 job 是深层级联**（L0→base 合并仅 31/2136）；
   逐层挂钟占比：**L5→L6 = 52.9%（50 GB）/ 48.4%（100 GB）**、L4→L5 = 27.7% / 35.6%，
   而 L0→L3 = 4.4% / 2.9%。L0 是这笔工作的**触发者**，深层级联是**成本主体**。

**按计划给的句式**：

> 在 W、C、R 下，深层级联产生的工作量对设备服务容量的占用是真正的端到端约束：
> 其债务（pending compaction bytes）以 +1.5 GiB/s 增长并钉在 64 GiB 软限，
> 而压实子系统退休该债务的服务率 μ ≈ 200 MB/s 与所有 worker 容量旋钮无关；
> 移除这笔工作量后前台吞吐提高 **9.9×（整轮）/ 10.2×（到达相位）**、MemTable 停顿行从 87 降到 **0**，
> 而对 Flush（F 1→4）、L0→base 与深层（C 2→12、SC 1→16）进行同等容量干预**没有收益**
> （全部落在 1.31× 的臂间带内，且提高压实并发会因键区间 100% 重叠导致 device WA 从 8.70 升到 9.40，反而变差）。
> 因此本场景下**不是某个阶段的线程服务能力不足，而是"设备容量 × 深层级联重写量"这一乘积**——
> 该结论与计划预设的三个候选（Flush 不足 / L0→base 串行不足 / 深层饱和）中的第三个方向一致，
> 但**把它从"深层 worker 不够"修正为"深层重写太多"**。

### 7.3 可操作含义（本场景实测）

| 手段 | 实测效果 | 证据 |
|---|---|---|
| 降低压实并发（C=12→2） | device WA 9.40→8.70，吞吐 1.14× | §5.2 |
| 单 subcompaction（SC=8→1） | device WA 9.12→8.46，吞吐 1.18×（本轮最高） | §5.2 |
| 增加任意阶段的 worker 数 | 无收益（噪声带内）；压实侧反而增加 WA | §5.1/§5.2/§5.3 |
| 改变到达次序使 L0 文件键区间不相交 | 旧报告 §4.1：SST WA 5.9× → **1.008×**、零 `L0→base` 重写、吞吐 48.7–73.6 K → **266.6 K ops/s** | `L0_INVESTIGATION_REPORT.md` §4.1 |
| 改变层几何/批量尺寸（`max_compaction_bytes`、`max_bytes_for_level_multiplier`） | **无效**：WA 仅降 2–2.5%，吞吐反降（0.71–0.76×） | §5.5 |
| 减少 LSM 层数（`num_levels`） | **引擎不允许**（已存在库层数不可下调） | §5.5/§8 |
| 与设备争用（注入 O_DIRECT 随机写） | 竞争者被从 61 MB/s 挤到 4.0 MB/s（−93%）→ 无空闲容量 | §5.6 |
| 移除压实工作量（`noc`） | 吞吐 **10.2×**、WA→1.02、停顿 87→0、p99 6.55 ms→113 µs | §5.4 |

**方法论要点**（本轮最重要的可复用结论）：在回放噪声达 1.3–2.5× 的环境里，
靠 ±20% 量级的容量旋钮扫描无法判定瓶颈；必须（a）用配对/交错设计压噪声，
（b）优先测量**低方差的物理量**（device WA 的 sd 仅 1–6%，是吞吐 sd 7–22% 的 1/4），
（c）用**期望效应为数量级**的干预（移除工作量、注入设备负载）做因果判定。

## 8. 已知限制

**继承 `bench/CAMPAIGN.md` §6 的限制**：单机单设备单 CF；无 NAND 级写入计量；
`Get` 的逐层探测计数不可得；"冷缓存"由块缓存大小模拟而非丢弃页缓存；后台 job 的
"eligible→scheduled" 调度等待不暴露。

**本报告新增的限制与未覆盖项**：

1. **压缩配置未复核**：本机预编译的 RocksDB 未链接任何压缩编解码器，全部运行 `compression=none`。
   计划 §一 要求"再用一种实际部署相关的压缩配置复核关键结论"——**未满足**，
   且这条对结论有实质影响：压缩会同时改变 flush/compaction 的 CPU 与字节量，
   `吞吐 ≈ μ/WA` 中的 μ 可能从"设备服务率"转向"编解码 CPU"。
2. **排序/编码/压缩的 CPU 时间不可分离**：RocksDB 不暴露 flush 内部的阶段划分，
   报告只给出整进程 CPU 核秒/GiB（隔离实验 §4.1）与 per-job CPU（§3.2）。
3. **compaction 的排队时间（eligible→scheduled）不可得**；报告以"池占用率 + 待压实债务 +
   限速状态"作为代理，并以固定输入重放（§4.2）补充。
4. **L0 与目标层的范围重叠度未在本 campaign 重新测量**：核心的"并发压实同层文件键区间 100% 重叠"
   来自旧报告的受控实验（`L0_INVESTIGATION_REPORT.md` §5.2，静态层级对照 7.4%）；本报告 §5.2
   引用该机制解释"C 越大 WA 越大"，但未在本阶段独立复测该量。
5. **每层的 I/O 时间不可得**：只有 per-job wall 与 CPU（CPU/wall = 0.14–0.23 表明 IO 受限，
   但无法把 wall 拆成 IO 等待与计算）。
6. **设备队列深度与设备级延迟未采集**：只有 `io_ticks` 忙率与带宽，另加独立的随机 IO 上限探针
   （§5.6 表）。`devbench` 的写侧数字（56 MB/s）受 ext4 分配/日志影响，
   是"设备+文件系统"的量，不等于 NAND 级能力。
7. **`num_levels` 下调不可行**（引擎拒绝），因此"减少级联层数"这一最直接的深层干预未测；
   仅测了 `max_bytes_for_level_multiplier` 与 `max_compaction_bytes` 两个较弱的几何杠杆。
8. **两个统计窗口给出相反排序**（§5.0c）：到达相位与稳态窗口的臂间排序不一致，
   说明 ±20% 量级的臂间差异不可判定。本报告的容量扫描结论是"无系统效应"，
   而不是"某臂更优"；存在**小于噪声带的真实效应被漏检**的可能（对 1.34× 带内的效应不敏感）。
9. **单臂 5 次重复不足以把 CI 收到 10% 以内**：等价对照 `default` vs `x_f2c6`
   的配对 sd 为 ±0.33（约 33%），即本轮设计能可靠检出的最小效应约在 1.5–2× 量级。
10. **`devload`(v1) 作废**（注入量不可核验）；`devload2` 的注入量本身只有 4–71 MB/s
   （受该设备随机 4 KiB 写上限 56 MB/s 制约），因此该臂的判据是"竞争者被挤到接近零"
   而非前台吞吐的百分比变化。
11. **一次机器重启 + 一次脚本并发编辑事故**：前者由运行级 `done_rc` 判据自动续跑，
    后者导致 `zipf` 首次调用语法错退出（重跑成功）；两者都在 `CAMPAIGN_BN.md` §3d 记录在案。
12. **重放实验 n=1/臂**（§4.2）：只用于部件成本，不进入因果判定。
13. **闭环饱和到达**：λ 是内生响应变量，不是外生固定的到达率；因此计划 §七 条件 1
    的"固定到达率下"在本实验中由"闭环持续背压下的稳态"代替，并在 §3.1b 以队列先后顺序呈现。
14. `--wait_for_drain` 的退出条件包含 `L0==0`，一个已沉降的库在 `L0 < level0_trigger` 时
    不满足该条件，导致部分运行等满上限（zipf 臂因此整轮时长不可用，§6 已按到达相位报告）。
15. `estimate-table-readers-mem` 在本构建中不可用（旧报告 §6 第 7 条），文件元数据内存
    以 RSS 与块缓存用量代替。
16. 冻结状态校验（`--mode=verify`）只在 54 个容量扫描运行上执行；`noc`/`zipf`/`geom`/
    `devload2`/隔离臂未跑该校验。它们使用同一固定种子轨迹与同一负载参数，但**其最终逻辑状态
    未经回读确认**（脚本级证据：轨迹由固定种子置换生成，运行日志中的 `ops=12800000` 与
    `U=12.40GB` 在各臂一致）。
